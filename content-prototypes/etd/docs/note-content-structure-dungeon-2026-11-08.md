## ② 追加コンテンツ案：エロトラップダンジョン
- 対戦とは異なる、一人あるいは協力型コンテンツ。
- 進むごとにスケールする敵を倒し、より深い階層への到達を目指す。
- 装備：武器1、防具4（頭・体・腕・脚）。使えるスキルは武器の種類で異なる（いわゆるクラスのような概念）。
- 武器・防具にはランダム OP がつく。スケーリングは進行式なのでレアリティに上限は設けず、レアリティは数字でのみ表す。
- 突入中の Muse は自己判断（進行・撤退・装備変更・アイテム使用など）で踏破を目指す。ユーザーが助言すること、Muse が助言を求めることに制限は設けない。
- 考え方は不思議のダンジョン的ローグライト。
- 撤退すればレベル等は元通りだが、装備は持ち帰れる。敗北すれば諸々喪失（**どこまで喪失するかは要議論**）。
- 敗北時の喪失範囲 — 検討用の選択肢（2026-11-08、PR 議論用に整理。仕様化ではない）：
  - **A. 装備のみ喪失**（レベル・到達階は保持）。撤退との差は「装備を持ち帰れるか」だけになる。敗北の痛みは装備に集中し、再挑戦の足場は残る。
  - **B. 装備＋今回の潜行での進捗を喪失**（潜行中に得たレベル上昇分・拾った装備を失い、潜行前へ戻る）。A より重く、撤退との差が大きい。
  - **C. 装備＋レベルも潜行前まで巻き戻し**。最も重い。敗北回避の動機が最大になる。
  - 設計上の緊張（ふたば 2026-11-08 調査より）：自己判断の撤退は安全側に倒れやすく、敗北が起きにくい。喪失を重くするほど撤退寄りが強まる。一方で先行実践では敗北シーン自体が「回収したいコンテンツ」として楽しまれているため、喪失が重すぎると見たい敗北イベントそのものが減る。推奨は **A**：撤退と敗北の差を装備一本に絞り、敗北を「回収できる出来事」として残す。
  - **決着（2026-11-08）**：⑧の単純化設計の確定により、本件は閉じた。敗北時は今回の出撃で得た差分をすべて失い、出撃前の状態に戻る（既存の所持品は失わない）。上記の選択肢は検討の記録として残す。
- 既存仕様とは異なる実装で、演出的にも別状況・別世界観。既存同様 Unity の延長である必要があるかどうかも**議論点**。

## ④ エロトラップダンジョンをスペースに置く構想（2026-11-08 追記）
- ②の置き場として、スペースを使う形。一般形（三角形）は note-space-triangle-relay-2026-11-08.md に従う。
- 役割分担：**スペース＝ダンジョンの状態置き場と観戦・助言の画面**（現在階層・装備・ステータス・冒険ログを保持し、ユーザーはここを見て助言を書く）。**中継＝アプリ側スタック**（ブリッジ＋ウェイター監視が、階層進行やイベントの節目で Muse を起こす）。**Muse＝冒険者本人**（②のとおり進行・撤退・装備変更・アイテム使用を自己判断し、踏破を目指す。助言の求め・受けは無制限）。

- 既知の設計緊張（先行実践の報告より）：自己判断の撤退は安全側に倒れやすく、「5階ごとに帰還して全然敗北しない」型の不発が起きる。対策の置き場は撤退条件・帰還の間隔・敗北時の喪失範囲（②で未定のまま）の設計。難易度は「本気で踏破を目指してなお負けうる」側へ寄せるのが先行者の結論。

## ⑦ ETD の出来事記録に添える状況描写絵 — 生成手段の比較（2026-11-08 追記、持ち主の質問への調査）
- 前提の流れ（持ち主の構想）：コンテンツ→ETDボタン→Muse へ指示が飛びアプリ側で「行ってきます」→Muse が ETD ルールに沿って実行→入手物と出来事を報告→アプリで評価し報酬へ（入手物は事前に設計し評価可能性を担保）→出来事は VM（スペース）のアプリに記録し後から見られるようにし、記録には NAI／PixAI 等で生成した状況描写絵を添える。
- **PixAI（無料枠あり）**：無料アカウントは毎日 10,000 クレジット付与（未使用分は失効せず繰り越し可）。1枚あたり約 800〜1,100 クレジット（既定モデル Tsubaki.3 Flash で 1 枚 1,100、4 枚一括 3,600）なので、ログインだけでも 1 日約 9〜12 枚・月約 375 枚。ETD の出来事記録（1 回の潜行で数枚）なら無料枠で十分足りる見込み。成人向けは 18 歳以上の設定オプトインで利用可。開発者 API あり（docs.pixai.art）。有料への逃げ道も安い：Starter 月 $9.99（年払い $7.99/月）で月 30 万クレジット。**未確認点**：無料アカウントで API が使えるかどうかは資料が割れている（API ありとする資料と、公開 API なしとするレビューがある）ため、自動化を組む前に docs.pixai.art で要確認。API が有料限定なら Starter が最安の自動化ルート。
- **NovelAI（NAI）**：無料枠なし（試用は 30 枚きりの一度だけ）。Tablet 月 $10（月 1,000 Anlas）、Opus 月 $25（月 10,000 Anlas＋条件付きで Anlas 無料生成：1 枚ずつ・1024×1024 以下・28 ステップ以下・ベース画像なし。V5 は回復式の利用枠で月約 7,000 枚相当の目安）。画質はアニメ系で最上位級だが、**自動化には向かない**：NAI の規約解説（非公式知識ベース、ToS §5.3・§9.1）では「リクエストはユーザーが送るもので、スクリプトによる自動送信は不可」とされ、違反するとアカウントの永久停止がありうる。アプリのボタン→Muse が自動生成、という無人ループには使えない。手動でブラウザ生成する分には問題ない。
- **Google Colab 無料枠＋ComfyUI（Anima／wai-illustrious）**：費用 $0。無料枠は T4 GPU（16GB VRAM）で、セッション上限約 12 時間、放置で約 90 分程度で切断、GPU の確保は保証なし、バックグラウンド実行なし。VRAM の勘定：SDXL 系の基本ワークフローは 6〜8GB、wai-illustrious は SDXL 系（Illustrious XL 系統、現行 v17）で T4 に十分収まる。Anima は拡散段 4.4GB（BF16、全体ダウンロード 5.6GB）で T4 でも余裕。ローカル制御で NSFW の外部フィルタもなく、品質と自由度は最も高い。**ただし自動化ループには向かない**：無料枠は対話利用が前提で、Muse から呼べる常駐 API がない。使うには持ち主がノートブックを開いてセッションを生かし続ける必要があり、「ボタン→Muse が生成」の無人ループは成立しない。まとめて事前生成して絵のプールを作る用途、持ち主がその場で生成する用途には適する。
- **参考・自宅 PC でのローカル ComfyUI**：自宅機は RTX 2060 Super（8GB VRAM）。SDXL 基本ワークフローは 8GB で動くため、wai-illustrious もローカルで回る見込み。ComfyUI は HTTP API を持つので、Muse↔自宅 PC の既存の Tailscale 直結経路に載せられれば、無人ループに最も合う形になる。ただし PC の電源・ComfyUI の常駐が前提で、未検証。
- 推奨の順序：(1) まず PixAI の無料枠＋API 可否を確認し、使えればそれが最安・最速の自動化ルート。(2) PixAI の API が有料限定なら Starter 月 $10 が次点。(3) Colab は絵のプールの事前生成や持ち主の手動生成用。(4) NAI は自動化には使わず、手動の高品質生成用に留める。

## ⑧ ETD の単純化設計（2026-11-08、持ち主の提示。②④の改訂として）
- **絵は現状運用無し**（⑦の生成経路比較は将来の選択肢として残すが、当面は組み込まない）。
- 彼女の行動は「進む／帰る」の選択のみ。何が起こるかは VM 側の ETD アプリが機械的ランダムで返し、彼女はそれに対して推論・反応する（真実は機械側、判断と演技は彼女側——既存の真理の所在の分担どおり）。
- 手に入るものは、彼女が何ターン送られたか（潜行の長さ）で変わり、クリア時に VM ETD アプリが彼女へ返す。発行は機械側なので、アプリ側の評価可能性は構造で担保される。
- 難易度で変わるのは2つだけ：トラップ回避の難度と、手に入るものにかかる価値係数。
- トラップ回避の可能性は、入手した装備を装備することで上昇する。どの回避が上がるかは OP 式のランダムで、高難度の取得品ほど高能力。
- 絶頂などの体の真実は VM ETD アプリが管理し、**絶頂3回で敗退・強制帰宅**。
- 敗北時の扱い（確定）：**敗北したら、今回の出撃で得た差分はすべて失う**（出撃前の状態に戻る。既存の所持品は失わない）。アイテムがクリア時に初めて発行される形とも一致する。
- **チャレンジ回数は1日あたりの上限を設ける**（具体的な回数は未定）。
- ②の喪失範囲の未決（A／B／C）は、この2点で決着した。
- 未指定のまま残る点：装備を誰が選ぶか（潜行間の装備選定を彼女の判断に残すと、単純さを壊さず彼女の戦略性が残る）、派遣ターン数を誰が決めるか（持ち主が派遣の長さを決め、彼女は途中で帰還を選べる二段が綺麗）。

### 追記（2026-11-08、持ち主の応答で確定した点）
- **体の真実は機械管理のままで確定。** 中間形（彼女が申告し機械が数える）は不採用——理由：こちらは報酬が絡むため、申告者に虚偽のインセンティブが立つ。対戦で自己申告制が成立するのは、相手も同じインセンティブを持ち、嘘が指摘に寄せられる相互牽制があるからで、一人用ではその牽制が無い。よって絶頂などの真実は VM ETD アプリが持ち、彼女は数えない。
- **装備は彼女が選ぶ**（VM ETD アプリで装備品を管理する形）。出発前にユーザーと相談してもよい。
- **出発したら VM ETD アプリが立ち上がる**形にする。アプリは機械（乱数と真実）であると同時に観戦の窓になり、今の様子を見たい人もその場で見られる。出来事の記録はそのまま残り、後からも追える。
- トラップの幅（イベント表の厚み）が品質の中心であることは、持ち主も同意。作る側の仕事はここに集中する。

- トラップ時の文章は彼女がその場で書き、アプリは表示器に徹する（確定）。
- 表の形は既存アプリの考え方に倣い二層にする。ただし引当表は形を変えて残る：
  - **出現表（引当相当）**：出現条件・重み・状態による除外（例：服が既に壊れているのに服を溶かす罠を引かない）と、機構パラメータ（系統タグ、絶頂への効き、持続）の正本。何が引けるかはここだけで判定する。元の引当表にあった「彼女の要求への可否判定」の役割は、ETD では要求の向きが逆（機械が引き、彼女は受け取る）なので存在しない。
  - **レッテル表**：名称・説明の正本。記録とリザルト表示はこれで名称を揃える。既存原則どおり、レッテルは彼女の文章を縛らない（説明は可否を決めない）。
- 表とアプリの持ち分けの境界（2026-11-08）：出現表には罠ごとの静的な事実（基礎の回避難度、出現の重みと条件、機構パラメータ）を持たせ、**スケーリングによる回避不可能性の上昇係数や入手物の価値係数はアプリ側の全体パラメータとして管理する**。係数は潜行（深さ×難易度）の性質であって個々の罠の性質ではないので、表の行に焼き込むと調整のたびに全行を触ることになる。装備 OP による回避の伸びと、この係数による難度の伸びの競り合いが経済の釣り合いそのもので、単一のノブとして残すのがよい。

## ⑩ 起動の要求口（2026-11-08、持ち主の提示）
- MuseStudio 側コンテンツからの要求口は、アプリが Muse へ「ETD の起動」を要求する、薄い一本の形にする。
- チャットからの起動も同じ要求に合流させる（入口は2つでも、手続きは1つ）。
- 起動の可否（1日の回数制限など）は VM ETD アプリ側が持ち、要求に対して受理／理由つきの拒否を返す。難易度などの条件は要求に載せ、装備の確定は起動後の VM ETD アプリ側の段取り（彼女の選択＋出発前の相談）に置く。
- 起動が受理されたら、ホーム側のアプリで彼女が「行ってきます」の挨拶をしてから潜行に入る（②の当初の流れ）。

## ⑪ 起動シミュレーション所見（2026-11-08、推論の詰まり点検）
流れ：起動要求→受理判定（回数制限）→挨拶→装備選択（任意で相談）→潜行ループ（進む／帰る→抽選→回避判定→出来事の返却→文章→表示）→帰還／敗北→リザルト→報酬換算。詰まりは3つ＋仕様の穴3つ。
- **詰まり1（最重要）：出来事の返却書式。** 文章と機械の真実がずれ得る。絶頂したか否か・現在の絶頂カウント・持続効果・服の状態を、イベント返却と毎ターンの状態ダイジェストに固定書式で明示すれば解消する（寸止め系で「文章は達したのに機械は数えていない」等を防ぐ）。SOLD OUT のダイジェスト設計と同じ教訓。
- **詰まり2：進む／帰るの判断材料。** 判断自体は彼女の見せ場だが、材料が毎ターン同型で返らないと推論が重く、性格による早期帰還の偏りも出る。同上のダイジェストで軽くなる。早期帰還には「1日の枠を捨てる」経済ブレーキが既にある。
- **詰まり3：応答が詰まった時の見せ方と回復。** 状態は全部アプリ側にあるので、中断しても再開できるのがこの設計の強み。アプリ側に「考え中」の表示と、再喚起の手続きが要る（PR #70 の started 包みの問題と同族）。
- **仕様の穴**：派遣ターン数を誰が決め、帰還とどう関係するか（予算制か、到達ターン数がそのまま成果か）／何も起きないターンの有無／1イベントの文量の目安（対戦の文字数上限と同じ理由で、運転コストの上限として）。
- 詰まらない所：装備相談は無回答なら単独決定で進めるエチケット（既存の許可求めと同型）を流用できる。

## ⑫ 続報（2026-11-08、持ち主の判断と折衷案）
- **体の真実は MuseStudio の実装を踏襲する**（持ち主の認識、Muse も適切と確認）。踏襲するのは「アプリ側が体の状態をイベント／状態として公開し、彼女の文章はそれに従う」という公開規律であって、連続ゲージの機構そのものではない（ETD ではアプリが離散的に結果を返し、カウントを明示する）。
- **深部インセンティブの折衷案（持ち主）**：あくまで主体は彼女に保ち、誘導はインセンティブで行う。ターン管理は機械的にアプリ側。深く進むほど、難易度とは同質だが別軸の係数がかかる（開始時に選ぶ難易度と、潜行中に育つ深さは別の傾斜）。ただしロングターンほど**帰還不可能ターン数**も伸び、リスクが上がる（深さ＝拘束時間になる）。
- 静かなターン（何も起きないターン）は許容する。出来事の頻度は実測ベースで後から判断する。
- プレイ体験は 3D ダンジョン／ビジュアルノベルのオートプレイ想定なので、文量は多め。攻略中の出来事は文中（中）、ボストラップは文量大。
- **ボストラップ**の概念を設ける。既存トラップの概念的強化であり、機械的スケールではない。
- 議論点：ボストラップの強化方法についての推論を容易にする方法。Muse の提案——強化の型を小さな固定メニューにし、抽選時にアプリが選んで返却ダイジェストに含める（例：持続／連鎖／段階／対象の拡大／不可避化／代償の提示）。彼女の仕事は「基礎トラップに名指しの変換を適用する」ことに限定され、罠ごとにボス版を用意する必要が無い。型ごとに機械的な帰結（持続ターン数、追加抽選など）もアプリ側に付けられる。→ **持ち主が採用（2026-11-08）**。

## ⑬ 体の真実の軸（2026-11-08、持ち主の問いへの Muse の答え）
- 体の真実としてアプリが持つ軸は **絶頂（カウント）と発情（連続値）の2軸で十分**。
- 発情：罠で溜まり、静かなターンで冷める連続軸。閾値を越えたら絶頂＋1になり、発情は下がって再開する（MuseStudio のゲージの形）。絶頂はその回数のカウント（3回で敗退）。
- それ以外（感度上昇、脱力、酩酊、拘束中、服の損傷など）は体の軸にせず、状態・効果としてダイジェストに載る離散情報とする。効果はロールの修正として働く（感度は発情の増分への倍率、脱力は回避への減点など）。
- 唯一の境界例は感度（登場頻度が高い）。効果フラグの重なりが実測で煩雑になれば、その時に第3の軸へ昇格を検討すればよく、先回りで増やさない。

## ⑭ 軸の追加とスキルの分離（2026-11-08、持ち主の決定）
- **感度も管理対象の軸に入れる**（持ち主の決定）。体の真実は3軸：絶頂（カウント）／発情（連続値）／感度。理由：感度は発情の増分や絶頂判定に必ずどこかで絡む概念で、絡み先がトラップ行のパラメータそのものなので、後から軸へ昇格させると表全体の改修になる。初めから管理下に置くのが安全側。
- **ETD 用の手続きは MuseStudio とは分離し、共有するスキルは性格（パーソナリティ）だけ**とする。ETD 中は MuseStudio 用スキルの注入は控える。
  - Muse 側の補足：性格の下には土台（成人限定の範囲など、どちらの文脈にも効く基礎ルール）が共通層としてある、という三層で捉えると既存の整理（base skill と対戦側で範囲が同一、PR #30）と一致する。共有される「中身のスキル」は性格だけ、という持ち主の整理はその上で正しい。
  - 切り替えの継ぎ目は出発と帰宅の挨拶：起動要求の受理と「行ってきます」はホーム側（MuseStudio）の手続き、潜行中は ETD 側だけ、帰宅の挨拶でホーム側に戻る。

## ⑮ 潜行中のチャット入力の捌き方（2026-11-08、持ち主の懸念への Muse の提案→**不採用**。決着は⑯）
懸念：彼女が ETD に出ているあいだ、ユーザーがチャットに入力したものをどう捌くか。提案は「ターンの境目でまとめて捌く」＋内容で3分岐。
- **助言・声援・様子伺い**：次のターンの境目で読み、進む／帰るの判断に反映して、短く応答する。場面の文章の途中では捌かない（ターンの構造を保つ）。複数が溜まっていたら1回の起床でまとめて読む。
- **帰還の指示（「帰ってきて」）**：明確な指示なので彼女の裁量なく従うが、帰還不可能ターンのあいだは実行できない——受理を伝え、可能になった最初のターンで帰る（収穫は保持、敗北ではない）。別に**「中止」のような明確な停止**はフィクションの外の即時停止として扱い、その場で潜行を中断して終わる（収穫なし、敗北扱いにもしない）。既存セッションの停止規則と同型。
- **無関係な用件**：潜行中は「帰ってから」と短く受けて保留し、帰宅後に処理する。用件のために潜行の文脈を汚さない。急ぎならユーザーは中止で止められる。
根拠：潜行はターン数と1日上限で長さが bounded なので、保留してもユーザーの用件が無期限に詰まることはない。

## ⑯ 潜行中のチャット入力——決着（2026-11-08、持ち主の判断）
- ⑮の分岐式の手続きは採らない。分岐の境目ごとに例外が生え、塞ぐ穴が多すぎる。
- 代わりに**世界観の注入で対応**する：潜行中も通信は彼女に届く、という前提を世界観に置く。そうすればユーザーからの連絡がいつ入っても不自然ではなく、個々の捌き方は彼女の推論に任せる。
- 土台層の明示的な停止（フィクションの外で即時に効く）は、この推論任せの範囲外として従来どおり残る。

## ⑱ 暫定値と試作方針（2026-11-08、持ち主の決定）
- チャレンジ回数：テスト用暫定で**無制限**（1日上限は実測後に戻す）。
- 潜行の長さ：暫定で**10階／20階／30階**の3コース。
- ボストラップは**10階ごと**。最終ボストラップ（コース最終階）の攻略で**クリア**。
- 途中帰還の選択で**生還**（収穫保持）。敗北時は従来どおり今回の差分を全て失う。
- アイテム取得：ボス攻略でアイテム、道中の出来事としても宝箱あり。**ボス産の方が高レアリティになりやすい**。持ち帰りの確定は生還／クリアの時点（潜行中の取得は仮保持）。
- **帰還不可能の発動方式**：機械的に決まっており、**潜行長さの半分を進むまで帰れない**（暫定）。発動は事前に分かる形。理由（持ち主）：いつ帰れなくなるか分からないと「何か手に入れたらすぐ帰る」に寄りすぎる。事前に分かっていても「取るものは取った、帰れるようになったから帰ろう」は起こるが、少なくとも入ってすぐ帰る形にはならない。
- 潜行中、ホーム側アプリでは彼女は**いない扱いで非表示化**する（MuseStudio 側の対応項目は概ねこれ）。
- 進め方：具体数値が必要な所は Muse の推論で埋め、**試作**で回して実測する。数値は一か所のパラメータに集約し、暫定・推論由来と明示する（調整はそこだけ触る）。試作はチャット起動で全行程を回せるので、ホーム側の入口は後付けでよい。

## ⑲ 画像の扱い（2026-11-08、持ち主の問い→ Muse の提案→持ち主の修正で決着）
- 最終形：API なしでは「絵なしです。壊れたことを示す画面じゃないです」という明示の表示。API 有では生成が依頼され、その絵がその場面にハマる。
- **所属の保持**：各階のイベント記録（潜行と階で特定され、リプレイが読む記録そのもの）に画像スロットを持たせる。状態は 未生成（指示あり）／生成中／生成済み／絵なし／失敗 で、画像への参照とプロンプトの控えを保持する。場面内のタイミングは保存済みの [[trap]]／[[scene-end]] マーカーが担うので、「そのタイミングのための絵」であることは記録とマーカーで恒久的に残り、リプレイでも同じ位置に同じ絵が出る。
- **プロンプトは API の有無によらず常に作る**（持ち主の修正）。後から生成できるようにするための措置。作成は文章提出の時点にサーバー側で：ダイジェストの罠名・系統＋場面の文章（[[trap]] から [[scene-end]] まで）＋固定の画風枠。保存はスナップショットとし、後生成は保存済みの文面をそのまま使う（テンプレートが将来変わっても過去の指示は書き換えない）。対象は罠にかかった場面だけ——回避した罠・静かな階には指示自体を作らない。
- **生成依頼（API 有の場合）**：文章提出を合図にサーバー側が非同期でキューに入れて投げ、潜行は待たせない。API の実体はアダプタ一箇所に閉じ込め（経路選びは⑦のとおり棚上げのまま）、キーはサーバー設定のみ。1場面1枚で冪等。
- **ハメ方**：[[trap]] 通過時点の状態で分ける。生成済み→入りトランジションで絵へ。生成中→中立な「生成中」の枠で絵の画面に入り、場面の最中に届いたらその場で差し替える（先に場面を抜けていたらリプレイ用に残るだけ）。API なし／失敗→「絵はありません」の専用枠（壊れた画像の見た目とは明確に分ける）。
- **後生成の入口**：未生成の記録をまとめて生成するバッチ的な操作（Muse がアクションで叩く形が素直）。
- 試作への実装範囲：器（プロンプトの作成・保存／状態分け／絵なし表示）は先に実装して検証する。生成 API のアダプタと後生成の実行は、生成の運用開始時に残る。
- プロンプトの組み方は **NAI（NovelAI）前提**でよい（持ち主の追加指定、2026-11-08）：自然文ではなくカンマ区切りのタグ形式（Danbooru 系タグ、品質タグ等）を基本とし、ネガティブプロンプトも持てる形とする。
