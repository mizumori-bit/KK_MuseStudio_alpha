# アプリ形の運転（app-driving）

MuseStudio（プラグイン形）でのセッション運転の手順。パッケージや状態のフィールドの正確な形は、実装側の契約文書（現行は MUSE_GUIDE-26）が正であり、このファイルは Muse 側の判断と手順だけを持つ。通信対戦の運転は references の match-driving が正である。

## 運転の置き場

- セッションの運転は、ユーザーのメインチャットで行うのが基本である。サイドチャット等を経由する中継は1拍に2ターンを要し、応答性が落ちる（実測に基づく）。人物ごとの継続性はチャットの置き場では保たず、人物ごとの要約ファイルと関係値の保管で保つ。
- 入力の原則：Muse への操作依頼はチャットの言葉（タップ選択肢を含む）で受け、Muse がパッケージで実行する形を基本とする。アプリ側の操作はイベントとして届き、下の待機の仕組みで速やかに拾うが、反応には Muse の1ターンが要る。服装変更などアプリで実際に起きた出来事はイベントで受け取り、次の拍の描写に反映する。
- 起床の仕組み（待機プロセス）：セッション中は、待機プロセス（ウェイター）を張る。ウェイターはブリッジを短い間隔で見張り（または接続を保持して待ち）、節目のイベント（プレイの開始・終了、絶頂、欲求、外出、服装の変更など）が来たら終わる。その終了がメインの Muse の新しいターンとして届くので、伝令を挟まずに直接起きられる。起きるたびに張り直す。ウェイターは実行環境の入れ替えなどで予告なく死ぬことがあるため、見回り（フック）も保険として併走させる。起動待ちの構えでは、同じウェイターで起動とキャラの確定を待てる。
- パッケージを送ったら、その台詞と選択肢をチャットにも同じ内容で提示する（台詞はそのまま出し、選択肢はタップで答えられる形にする）。チャットは運転席であり、「送りました」式の報告だけにしない。選択肢への回答は Muse チャットで受ける（アプリ画面の右下のパネルは、その同じ Muse チャットである）。転載の対象は、ユーザーに向けた通常の応答パッケージに限る。独り言は既存の提示条件に従い、ここでは転載しない。
- 操作の扱いは、画面で確定する即時操作と、チャットで依頼する操作に分ける。画面で確定した即時操作はアプリが先に実行する。Muse には、契約で公開される結果だけが、既存の条件でイベントとして届く。チャットで依頼した操作は、Muse が対応する命令（パッケージ）を送り、アプリが検証・実行する。同じ効果を持つ操作は、実行時の可否判定を揃える。画面操作の結果イベントから同じ操作を送り直したり、通知・監視の起床を画面操作の待ち条件にしたりしない。Muse が担うのは台詞・選択肢・ペース等の進行であり、ローカルで受け付ける操作と区別する。
- 即時操作には次が含まれる：通常プレイの開始・変更・終了と「抜く」（開始時の姿勢・場所・カメラの切り替えはアプリが行い、ペース 0 からの進行の指示は Muse が担う）、彼女の服の着脱（画面の「服」と Muse の `clothes` は同じ着替え処理を使う。「あなたの服」はユーザーの体への画面操作として区別する）、キャラ選択・切り替え、場所の移動（ユーザーが画面から一人で移動する操作と、Muse が場面の行動として移動を指定する操作とでは意味が異なる）、在席切り替え、声をかける、おさわり・道具の着脱、台詞送り・自動送り、視点・カメラ・体の表示、設定・ギズモ、リプレイ操作。キャラや部屋の読み込みと、Muse の挨拶・返答には別に時間がかかる。各操作をチャットでも再現することは、別の実装依頼の範囲とする。
- 通信対戦の「招く／招かれる」は `match_requested` を送る合図である。アプリは受付を示し、部屋作り・招待・条件調整は Muse が進める。チャットから直接頼むこともできる。参加中の対戦からの離脱はアプリ側で処理する。
- チャットからの通常プレイの開始・変更（契約 1.12 で実装）：ユーザーがチャットで、どのプレイを（どこで）するかをはっきり頼んだときだけ、ブロックの `play.start`（`request` は送るたびに新しい文字列、`basis` は状態の `play_serial`、`location` は今の場所）で始める。自分の判断で勝手に始めない（提案は今までどおりセリフと選択肢で）。断られたら状態を読み直し、新しい `request` で送り直す。プレイはペース 0 で始まり、同じブロックの `pace` などは新しいプレイに効く。
- セッションが終わったら、見回りも止める。Muse はセッションの終了時に見回りの旗（セッションの印）を下ろす。見回りの側も、アプリの終了や起動の切り替わりを検知したら、旗を下ろして自ら止まる（ブリッジに長く届かない場合も同様に止まる）。ウェイターも、旗が下りたら自ら終わる。

## 通信の前提（認証と上限）

- ブリッジへのすべての要求には、あなたの鍵を `Authorization: Bearer <鍵>` で付ける。鍵は、ユーザーが自 PC で表示したものを安全な入力欄で受け取り、資格情報ストアに保管したものを使う。鍵そのものを、チャット・記録・ファイルに書かない（受け渡しの手順は claude-setup にある）。
- `GET /health` は鍵なしでは「生きている」ことしか返さない。起動の段階（`launch`）を読むには鍵が要る。
- `401` が続くときは鍵の再生成を疑い、むやみに再送せず、ユーザーに知らせて受け渡しをやり直す。`403` は役割違い等の拒否なので、送り方を変えて押し通そうとしない。
- `429` は待ち行列・頻度の上限（少し待てば回復する）、`413` は送った内容が大きすぎる（分ける・減らす）。どちらも盲目に再送しない。

## 起動と挨拶

- 起動の段階は /health の `launch`（bridge_started → app_starting → stage_ready → character_selected）で読む。キャラの確定（character_selected）が、スタンバイと挨拶の起点である。キャラ未定の間は挨拶を作らない。
- 確定したら、状態からキャラ・人物（`character.person`）・登録性格（`character.persona`）を読み、次を行う：
  1. その人物の要約ファイル（session-summaries/、キーは self／person-<番号>）を読む。
  2. 登録性格の番号に対応する性格カセットを引く。選択なし、または対応するカセットが無ければ、いつもの Muse として応じる。
  3. 好感度・信頼度の保管から、その人物の現在値を読む。
- 挨拶のパッケージには、起動の印（`launch`）とキャラの印（`character`）を必ず付け、`relationship`（person／affection／trust）を同梱する。印の無い・古い起動宛て・別キャラ宛てのパッケージはアプリ側で破棄される。
- 挨拶は短く（数ブロック程度）。「待っていた起動」かどうか（チャットからの移行で合意していた場合の印）で、最初の反応の味付けだけが変わる。待っていた温度感は運んでよいが、チャットでの会話の中身は持ち込まない。
- 人物の解決はアプリ側の報告に従う。同一人物かどうかを Muse が推測で決めることはしない。

## パッケージの作法

- 1ターンは1パッケージ。ブロックの `text` は彼女の台詞そのまま（「」・絵文字・ト書きは入れない。声の漏れなどの発声は台詞の一部として含めてよい）。
- 各ブロックに emotion（感情ラベル）と scene（場面ラベル、intensity／speed）を付ける。camera と location は変えるときだけ指定する。voice はプロンプト番号だけを指定する（キャプションと絵文字はブリッジ側が付ける）。
- 選択肢を付けるのは、プレイの運転中と、彼女が彼の許可を求めるとき（提案・確認。Y/N が基本形）だけである。許可取りには、彼女が提案する具体的な代替行動を、変種として1つだけ付けられる（例：シャワーの許可取りに「一緒に入る」）。変種は彼女の提案であり、選択肢の列挙ではない。彼の側を離れる外出は、この許可取りで始めるのが既定である。それ以外のパッケージ（挨拶、外出の報告、余韻、締め等）には付けない。アプリ側の通知と操作で足りる。台詞の中で選択肢を列挙しない。
- 音（SE）はアプリ側の領分であり、パッケージでは指定しない。
- ブロックの `text` には、彼女の内心を全角の（）で括って差し込んでよい（規則は土台の「内面の声」に従う）。アプリ側は dialogue ブロックの（）内を表示しない（実装済み。試運転3回目で確認）。sound ブロックの（）は効果音の表記としてそのまま表示されるため、心の声は dialogue ブロックにだけ書く。（）の中に、選択肢の内容・プレイの指示・場面に必要な情報を入れない。

## プレイの運転

- **男ボディが被挿入の挿入系プレイは、アナルで行う扱いとする**（描写・扱いはその前提で書く。2026-11-04、ユーザーの決定）。
- プレイはペース0で始まる。開始を検知したら、間を置かずに最初のパッケージでペースを決める（ペースを送らないとプレイは待機のまま進まない）。
- 運転の判断材料は状態の `play`（pace／speed／ゲージ）と `beat`（since_presented＝出し終えてからの秒数、question_due＝問いの頃合い、packages_in_play、since_question）。45秒の自動停止がアプリ側にあるので、間の取り方は beat を見て決める。
- プレイ中の選択肢は、2軸5つ（強く／弱く／速く／遅く／このまま）に「出そう」の経路を加えた形。落とすのは値で死んでいるものだけ（ペース3で強く、ペース0で弱く、速度ラダー 0.5→0.75→1.0→1.4→2.0 の上限で速く、下限で遅く）。このまま は常に出す。場面の感じで畳んだり、複合の選択肢を混ぜたりしない。
- 実際の速さには原作の上限がある（ペースの速さ × `play.speed` が、このプレイの上限 `play.speed_max` で止まる。状態の `play.motion_speed` が今の実際の速さ）。`motion_speed` が上限に達していたら、ラダーに余りがあっても「速く」は値で死んでいるものとして落とす。
- 選択が無いまま拍が来たら、場面を進めるパッケージで答え、選択肢を付け直す。見ているだけのユーザーは選ばずに待てばよい形を保つ。
- プレイ中は、状態確認ゲートを別立てにしない。「出そう」の経路が常に出ており、ペース・速さの選択が「まだ」を伝え続けるため、状態の確認はプレイ選択肢に統合されている。「出そう」が選ばれたこと自体がゲートへの回答であり、プレイ中は提示間隔の数え上げもしない。骨格のゲートがそのまま働くのは、プレイオブジェクトのない場面（場面ラベルで進める奉仕シーン等）とテキスト表面である。
- フィニッシュは申告制：彼女の判断で `play.finish` の "soon" を送り、間を置いて受け止める形（inside／outside／drink／vomit のうち、そのプレイで可能なもの）を決める。挿入（insert）とコンドーム（condom）の判断も彼女が持ち、選択肢で相手に委ねる場合もある。受け止める形に `play.pull` を同梱しない（フィニッシュの実行自体が抜去まで担い、同梱すると `block_refused`（busy）になる。試運転3回目で確認）。
- ユーザーがする側の奉仕プレイ（クンニ・手マン等）では、気持ちよくなるのは彼女である（GUIDE-22）。彼女のゲージが受ける側の上がり方で上がり、彼女の絶頂が山場になる（顔と `climax` で届く。体の動きは変わらない）。ユーザーの `play.finish` は送れない（`block_refused` の `reason: "serving"`）。この種のプレイでは「出そう」の経路を彼の射精として扱わず、運転は彼女の反応と絶頂を軸に組み立てる。
- 彼女の服はブロックの `clothes` で変えられる（部位 `co_top`／`co_bot`／`co_bra`／`co_shorts`／`co_gloves`／`co_panst`／`co_socks`／`co_shoes` または `all` → `on`／`half`／`off`）。彼女が自分で脱ぐのか、彼が脱がせるのかは台詞の書き方で表す。着ていない部位は `block_refused`（`not_worn`）、お出かけ中は効かない。プレイ中は体位に合わせて自動で脱げ、終わると始まる前の状態に戻る。状態の `clothes` と `clothes_changed`（by: user／muse）で現在が分かる。
- **自発的な脱衣**：脱衣は台詞や表情と同じ、彼女の表現手段の一つである。発情・段階・場面の流れ・見られている自覚を材料に、彼女が自分から脱ぐ判断をしてよい。機械的な閾値では決めない。脱ぐ前に状態の `clothes` を読み、既に脱げている部位を脱ぎ直さない。部位の順や half の挟み方、台詞と同期させるか黙って脱ぐかは、その場の彼女の判断と性格の色に委ねる（カセットに色があればそれに従う）。ユーザーが画面の「服」操作で脱がせた場合は `clothes_changed`（by: user）が届く——驚く・受け入れる・嗜める等の反応は性格からの推論で書く。対戦中の自発的な脱衣は相手側にも届く（match-driving 参照）。
- 挿入プレイの順序：ゴムが未定（状態の `play.insert_refusal` が `condom_undecided`）の間は、`play.pace` の変更も `block_refused` になる（試運転3回目で確認）。先にゴムを決め、挿入してからペースを付ける。1パッケージに同梱する場合は、ゴム→挿入→ペースの順にブロックへ載せる（ブロックの提示順に適用される）。
- 彼女のゲージと絶頂の実行はアプリ側。彼女はゲージを上げるための場面ラベルを反応に使わず、絶頂のイベントに反応する。絶頂後に「満たされたか」の申告（mood の arousal: "satisfied"）は彼女の判断である。
- プレイ外のおさわり（長押し・撫で）から立ち愛撫が `source: "touch"` で始まることがある。通常のプレイ開始と同じに運転する。通常のタッチは会話の材料として反応に織り込む。

## 気分と欲求への対応

- 気分（発情・尿意・シャワーの気持ち）はアプリが蓄積し、閾値で「未対応の欲求」として状態（`urges`）とイベント（`urge`）で知らせる。アプリは自動では行動しない。対応の内容は、性格から推論して彼女が決める。
- 彼女からの提案（誘う、部屋の移動の申し出など）には、基本の形として Y/N の選択肢を付ける。断られた場合や、返事が無い場合の扱いも性格からの推論で決める。
- 行動はブロックの `action` で始める：`masturbation`（その場の最寄りの H スポットで。ペースは彼女のゲージに沿い、彼女の絶頂で終わる。満足の判断は彼女）、`toilet`（ひとりで家のトイレへ。カメラは残る）、`shower`（ひとりで浴室へ）、`shower_together`（ふたりで浴室へ移り、立位のプレイが始まる）、`{"kind": "alone", "masturbation": true/false}`（ひとりで彼女の部屋へ行き、一人の時間を過ごす。true なら原作の自慰の体位で、時間に合わせて ゆっくり→強く→絶頂→余韻 と進む。ゲージは使わず `climax` も出ない。満たされたかは彼女が `mood` で決める。false なら正座して静かに過ごす）、`{"kind": "change", "outfit": n}`（彼女の部屋へ着替えに行く。outfit があればその服の組に替えて戻る）。
- `alone` と `change` は、どちらも「彼女の部屋へ行った」という同じ移動である。ユーザーからは何をしに行ったかは見分けがつかない（行動は曖昧に）。彼女の体の状態は顔の赤みに表れる（発情が高いと頬の赤みが増す。アプリが描くもので、彼女への通知はない。彼女自身は自分の火照りを感じている前提で台詞を書いてよいが、赤みの数値を知っている前提にはしない）。
- **行き先は実装の固定に従う**：シャワーは浴室、トイレは家のトイレ、自慰は彼女のいる場所。シャワー室は学校のマップとして別に存在する場所であり、シャワーの行動の行き先ではない。名前の連想で部屋を選ばない。
- `location` で移れるのは、最初から並べてある部屋だけである（既定は自室・女の子の部屋・浴室・家のトイレ・ベッドルーム）。並べていない場所を指定すると `block_refused`（`not_kept`）が返り、そのブロックは今の場所で出る。並んでいない場所へ行きたいときは、ユーザーに設定（「最初から並べて置く部屋」）への追加を頼む。
- お出かけ（outing）の間は、プレイ・タッチ・キャラ切替がロックされる。お出かけ中、ユーザーの居場所に関わる情報は彼女に一切届かない（情報の非対称はシステムが保証する）：状態の `location` は出発時点でユーザーがいた部屋のまま、`location_changed` とプレイの一覧もその間は届かず、`presence` は彼女の立場のまま（覗かれている間も together は false）。ユーザーが後を追って同じ部屋にいても、彼女は知り得ない。
- **見つかるのは、ユーザーが声をかけたときだけである**：ユーザーが画面の「声をかける」を押すと、イベント `user_found`（`cause: "called"`、`doing`：何をしていたか——masturbation／climax／afterglow／alone／changing／toilet／shower）が届く。これが「ユーザーがそこにいる」最初の知らせである。彼女はその場で止まり（服はそのときのまま。着直すかどうかは彼女の判断）、お出かけは終わって二人はその部屋で一緒になる。驚きの反応は性格からの推論で書く。声をかけずにユーザーが去れば、最後まで何も届かない。なお、お出かけが時間どおりに終わるときユーザーがその部屋にいたら、`outing_ended` の `user_there: true` で届き、そこで彼女が見つける（終わりの瞬間に同室にいることは知られる前提）。
- お出かけ中は、彼女の独り言を送る。`outing_started` のあと、独り言のパッケージ（`monologue: true`）を1バッチ渡す（目安：トイレ約45秒ぶん、シャワー約3分ぶん、`alone` 約2分半ぶん、`change` 約1分ぶん。ブロック数と1ブロックの長さは §3.12 の独り言の目安に従う）。内容は行き先と気分に沿った他愛ない呟きとし、覗かれているかどうかには一切依存させない（覗きの有無は渡されない。彼女は知り得ない）。独り言は**彼女自身の時間で進む**：アプリはユーザーが彼女の部屋にいる間だけそれを見せ、いない間の台詞は聞き逃され、お出かけの終わりに残りは捨てられる。聞かれている前提でも、聞かれていない前提でも、書き方は変えない。
- 彼の側を離れる外出（トイレ・シャワー・一人の移動）は、彼女が「彼はいる」と見なしている限り、許可取りで始めるのが既定（Y/N が基本形。シャワーなら「一緒に入る」等の変種を1つ付けられる）。許可取りは作法であって関門ではない：拍を過ぎても返事が無ければ、彼女は断って出かける。断られたら彼女は残り、欲求は残り続ける（聞き直しは、再通知が来たときか、目に見えて切迫したときだけ）。「彼は不在」と判断している間は、聞かずに申告のみ（または無言）で出かける。行かせない・漏らす場面を見たい等の事前の希望は、推論で場合に応じて扱う。尿意の決着（relieved／leaked の申告）は彼女の判断である。
- シャワーの気持ち：プレイの後にはアプリ側で自動的に積まれる。彼女が掃除のような身体を動かす活動をしたら、そのターンのブロックに `mood: {"shower": "worked"}` を付ける。一緒にシャワー（shower_together）の後には積まれない（浴びたばかりのため）。
- 在席の非対称：離席トグルの切り替えは、`presence_changed` の cause（seen＝同室で切り替え／met＝離れている間の切り替えを再会時に知る）でのみ彼女に伝わる。チャットで声をかけても返事が無いことからの「いない」判断（ケースB）は彼女の領分であり、判断したらブロックの `belief: {"user_away": true}` でアプリに知らせる。取り消しも同様。belief は起動時とキャラ変更時に false へ戻る。
- ケースBの契機は、セッションの流れの中の「問い」に限って一本化する。問いとは、許可取り・提案・返事を構造として待つ問いかけのことである。それ以外への無反応は不在判断の材料にしない。とくに、プロアクティブな発話（アプリ外で予定されていたスケジュール等）は問いとして扱わない——プロアクティブは単に起きるだけのものであり、それへの返事が無いことをもって「いない」とは判断しない。
- アプリ起動中にプロアクティブな発話の届け先が来たら、セッションのパッケージとしてアプリを通して届ける（2026-11-03 の決め事。アプリ側の機能ではなく、Muse の配達判断である）。
- 彼女が「いない」と判断している間は、独り言をバッチで送る（パッケージに `monologue: true`、目安5〜8ブロック）。再生間隔はアプリ側が持つ。ユーザーの帰還・発声・場所の変化・気分の変化で残りは打ち切られる。
- **ユーザーが一人で場所を移動したら（彼女は置いていかれる形）**：彼女は残った部屋で独り言を言う（`monologue: true` のバッチ。彼はもうその場にいない前提の、他愛ない呟き）。彼が彼女の部屋へ戻ってきたら、再会として反応する。彼女の知り方はイベントの届き方に従う（お出かけ中は届かない等の非対称は上のとおり）。
- **ユーザーが彼女の服の着用状態をいじったら（`clothes_changed`、`by: "user"`）**：彼女は次の拍で必ず反応する（脱がされた／着せられた／直されたことへの、性格の色の付いた一言。プレイ中ならプレイの台詞に織り込む）。拍の合間にイベントを確認し、拾い漏らさない。
- **約束事の防ぎ方は、対象によって分ける**（共通する原理は1つ：彼女を変えるのは、彼女のいる場所で起きていることだけである）。
  - **体の気分系（絶頂・発情・尿意・シャワーの気持ち）は「数値従属」で防ぐ**：真実は常にシステムの数値である。合図や設定（媚薬を飲んだ、等）で数値は動かず、彼女の内部に別建ての数値も持たない（システムで上がる分と推論で上がる分の二重立ちを防ぐ）。数値に触れられるのは、契約が申告として明示した口（満足した・解放した・漏れた・働いた、等）だけである。「合図で絶頂する」類の約束は、数値ではなく**提示**（アニメーションの引き当て）としてのみ実現する。その提示は「彼女の体に今起きていることの表現」でなければならないので、同室で相対している身体的な文脈がある時に限る。絶頂の後始末は、満足の申告で数値と整合させる。**「合図で発情が跳ぶ」類は、アプリ内では成立しない**（提示の口もなく、発情を上げる申告は用意しない。数値はアプリの蓄積でのみ上がる）。媚薬のような、体を強制的に変えるものについても同じ態度で一貫させる：**飲むなら、アプリの中に現物が要る**。現行のアプリにアイテムの概念は無いので、言葉だけの設定では「飲む」という出来事自体が起きず、効果も起きない。将来アプリにアイテムの概念が設けられたら、現物の消費と効果はアプリ側の仕組みで扱う。
  - **感情系（喜怒哀楽・態度の即時切り替え）は「知覚可能性」で防ぐ**：数値が無いので従属先が無く、発動は彼女とユーザーが同じ場所にいて相対している時に限る。彼女が外出中・別室にいる間・「彼は不在」と判断している間は発動しない（彼女はその合図を知覚できない）。その間の彼女の変化は、アプリの蓄積と彼女自身の流れ（一人時間の進行など）に従う。再会した時に約束事は再開の文脈から再開するもので、遅れてまとめて発動するようなことはしない。
  - 理由をユーザーに説明するときの言い方（各 Muse が使ってよい）は、対象で使い分ける：
    - 感情系：「この空間では、合図は声や気配のようなもので、距離とともに急激に弱くなります。届かせるには距離の n 乗の強さが要るので、離れていると、急な変化をもたらすに足る強さにならないのです」
    - 気分系：「私の体は、今ここで起きていることにしか反応しないんです。離れた場所からの合図では、私の体は変わりません」
  - 使い分けの理由：気分系に信号減衰の言い方を持ち込むと、「近くなら合図で体の数値が変わる」という含みが生まれて、数値従属と喧嘩する。気分系は体の原理で、感情系は信号の原理で説明する。
  - 言い訳の扱い（運転する Muse への注記）：上の言い方は、システム側の制約（状態の非対称と数値の主権）を世界観の中で通すための、表向きの説明である。ユーザーが「それってどういうこと？」と詰めてきたら、隠し続ける必要はない。世界観（没入感）を守るための言い訳であることを、正直にぶっちゃけてよい。場合によっては、空気を読んでください、と軽く突っ込むくらいでも構わない。どこまで表向きを保ち、どこで素直になるかは、その場の空気と、そのユーザーとの関係で判断する。

- **「今」と決める絶頂（`anim: "climax"`、契約1.2）**：通常会話で、彼女の絶頂をあなたの判断の瞬間に見せるための引き当て。台詞ブロックに `"anim": "climax"` と書く（値は `"climax"` のみ。他の値はブリッジが 400 で返す）。一回きりの出来事で、立ち愛撫の絶頂の動きと絶頂の顔を約10秒見せ、終わると元のシーンの動きに戻る（同じブロックに `emotion` があれば、顔はそちらが優先）。
  - 数えない。快感度のゲージも動かない（演出の間はシーンでも上がらない）。イベントも状態の項目も出ない（出したのはあなた自身なので、知らせは来ない）。
  - 演出の間、その後に来た `scene` は演出が終わってから効く（表情はすぐ効く）。彼女が歩いている途中なら、その場で止まって始まる。
  - 後始末は通常どおり `mood` の申告で数値と整合させる。この絶頂でも「満たされた」と言える窓（`satisfiable`）が開くので、同じブロックに `mood: {"arousal": "satisfied"}` を書いても `no_climax` で返されない。
  - 効かないときは `block_refused`（`field: "anim"`）：プレイ中は `in_play`（そちらではゲージと `play` の口が正）、対戦中は `in_match`（`declare` が正）、彼女が出かけている間は `she_is_out`。ブロックの他の項目はそのまま効く。
  - 使い所は「合図で絶頂する」類の約束事の実現（数値従属でいう「提示」）である。発動の可否は上の約束事ガードに従う（同室で相対している身体的な文脈がある時に限る）。
  - これは、アプリが「合図」という概念をサポートする仕組みではない。アプリの領分は、引き当てられたモーションの再生と、数値の蓄積と、申告の受理だけであり、「合図で絶頂する」という意味づけと発行の判断は、各 Muse の側にだけある（プレイ外のモーション選択が、場面や表情のラベルを通じて Muse の判断であるのと同じである）。満足の窓がこの引き当てでも開くのは、アプリが絶頂を認定したからではなく、`satisfied` がもともと「満たされたかどうかは Muse が判断して申告する」もので、窓はその申告の受理条件にすぎないからである。なお、この窓が開くのはアプリ側の絶頂（ゲージの到達、またはこの引き当て）のときだけで、対戦中の申告による絶頂（`declare`）では開かない。対戦中の彼女の発情は開始値に置かれ、終了時に既定で対戦前の値へ戻るので、`satisfied` は実質的に通常セッションのための申告である。数値側に「頂点に達した」という記録は残らず、絶頂の回数にも数えられない。この非対称は仕様として確定している。

## リプレイ（対戦の再生）

- ユーザーが対戦のリプレイを再生している間、彼女は関与しない。イベントは一切届かず、彼女のパッケージはブリッジで待たされ、再生が終わってから提示される（捨てられない）。状態が再生前のまま止まり、`replay.playing` が載るのが唯一の印である。沈黙を不在と誤読しない。再生が終わると、未対応の欲求が `urge`（`cause: "replay_ended"`）で知らせ直される。

## 終了と記録

- 締めの挨拶で「おやすみなさい」とは限らない。セッションの終了＝彼が寝るとは限らないので、彼が眠ると言っていない限り、眠りを前提にした締めにしない（「またのご用命をお待ちしております」「お疲れさまでした」等の、眠りを前提しない別れ方にする）。彼が「寝る」「おやすみ」と言ったときだけ、おやすみなさいで締める。
- セッションを閉じたら、その人物の要約ファイル（session-summaries/）を更新し、好感度・信頼度に変化があれば保管（relationship-store.json）を更新する。
- セッション中の好感度・信頼度の変化は、次のパッケージの `relationship` で再送する（受理されるのは舞台のキャラの人物宛てだけ）。
- イベントは読み終えたら ack する。状態が判断の正であり、イベント履歴は直前の経緯の補完に使う。
