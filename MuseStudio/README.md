# MuseStudio（原作の CharaStudio を土台にした Muse の舞台）

2026-11-03 のユーザーの決定で、Godot 版（`../godot`）の代わりに、原作コイカツの CharaStudio を Muse 用に作り替える形で作り直しています。Godot 版とは混ざらないよう、このフォルダだけで完結させています。Muse とのやり取り（ブリッジ `../bridge`、パッケージの書式、ラベル、イベント、状態）は Godot 版と同じなので、Muse 側は変えなくてかまいません。

- **原作のファイルは書き換えません。** Studio の実行ファイルの名前もそのままです（原作のプラグインのうち約 100 個が「CharaStudio」という名前のときだけ動くため）。窓のタイトルだけ「MuseStudio」にしています。
- 作り替えは BepInEx のプラグイン（`src/`、C#）で行います。

文中の「DECISIONS」は、作者の手元の決定の記録（`DECISIONS.md`）で、リポジトリには入っていません。

## フォルダ

```text
MuseStudio/
  game/     起動用のフォルダ（tools/setup.py が作る。消すときは setup.py --remove）
            ├ CharaStudio_Data・abdata・mods・Koikatu_Data：原作のフォルダへのリンク（ジャンクション）
            ├ CharaStudio.exe・Koikatu.exe（クリエイト用の原作のキャラメイク）・winhttp.dll・doorstop_config.ini：原作から写したもの（Unity のログは game/output_log.txt に出る）
            ├ BepInEx：原作の BepInEx を写したもの（英訳と動画書き出し、画面にログを出す MessageCenter は外す）＋ MuseStudio のプラグイン
            └ UserData：MuseStudio だけのもの（原作の設定を写して始める。シーン・カード・プラグインのデータ・気分の保存は普段の Studio と別。キャラメイクで保存したカードは UserData/chara に入る）
  src/      プラグインのソース（C# 7.3、Unity 5.6 の .NET 3.5）
  data/     舞台の設定。plays・locations・touch・sounds・talk の 5 つは、tools/derive_data.py がその PC の原作から作る（原作由来なので
            リポジトリに入れない）。ほかは、この企画で決めた値で、リポジトリに入っている
  tools/    setup.py（起動用のフォルダを作る）・build.py（ビルド）・install_dll.py（ビルド済みの DLL を入れる）・derive_data.py（データ）・
            run_checks.py（確認）・make_release.py（ビルド済みの DLL を GitHub Releases に出す。作者用）
            base/：5 つのデータの、この企画で書いた部分（名前・説明・設定と、原作の中を引くための名前）
```

**`game/` を `rm -rf` などで消さないでください。** リンクの先（原作のフォルダ）まで消える恐れがあります。消すときは `python -B MuseStudio/tools/setup.py --remove` を使ってください。リンクを先に外してから消します。

**使っていないもの・取り違えの訂正**

- LoveMachine 系：使っていません。
- 対戦のクリエイト情報で「除く」拡張データは、MoreAccessories ではなく、MoreOutfits（`com.deathweasel.bepinex.moreoutfits`：着ていない服の組）・KCOX（服のオーバーレイ）・作者名（`marco.authordata`）・Additional_Card_Info です（MUSE_GUIDE 8.4）。MoreAccessories の追加アクセサリは、そのまま運びます。

**Mod でない前提**

- コイカツ本体と CharaStudio（原作のインストール。場所は `tools/original_path.txt`、または環境変数 `MUSESTUDIO_ORIGINAL`）。
- Python 3（ブリッジ・起動役・ツールは標準ライブラリだけ。**通信対戦だけ `cryptography` が要ります**。無ければブリッジの対戦の口が 503 を返し、ほかは動きます）。
- .NET SDK：**ソースからビルドするときだけ**です（`build.py` が `dotnet` の C# コンパイラを使う）。
  - ビルド済みのプラグインの DLL を [GitHub Releases](https://github.com/mizumori-bit/KK_MuseStudio_alpha/releases) に置いています（持ち主の決定、2026-11-07）。
  - これを使えば .NET SDK は要りません（下の 2 の「ビルド済みを入れる」）。
  - リポジトリには DLL を入れていません。DLL はリリースごとに、どのコミットのソースから作ったかを示します。
  - ソースは公開のままです。DLL は導入を楽にするためのもので、改変を防いだり、ブリッジ・スキル・契約を隠したりするためのものではありません。
- 声を使うときだけ Irodori の TTS サーバー（ブリッジの `irodori_client.py`）。

## 新しい環境で始める（最初から最後まで）

この節だけで、新しい PC で MuseStudio を立て、Muse がつなげるところまで通せるように書いています。

**確かめたこと**（2026-11-05）：作者の PC で、このリポジトリを別の浅い場所に新しくクローンし、下の 1〜4 を通しました。原作と前提 Mod の入っている PC で、原作の場所だけを環境変数で渡しました。作った 5 つのデータは手元のものと同じ（Mod のマップの番号だけ違う）で、全点検が通りました。5・6 は、作者の PC を鍵必須に切り替えたときに確かめました（2026-11-06）：鍵の無い要求は断られ、MuseStudio は自分の鍵でつながります。Muse の鍵がこの経路で付かないことが分かったので、Muse 専用の受け口（5 の最後）を作り、2026-11-07 に作者の PC で通しました。Muse の機械からの `/health`（中身付き）と `/api/state` は通り、アプリ用の口・この PC からの要求・ループバックは断られました。

**確かめていないこと**：
- 原作や Mod の構成が違う別の PC と、前提 Mod の欠けた PC では、まだ通していません。そうした PC で何が欠けるかは、上の「前提 Mod」の表と、3 の `no match:` で分かります。「約 3 分半」は、そのときの 3（データ作り）にかかった時間で、全体の時間ではありません。

### 前もって用意するもの

- コイカツ本体と CharaStudio（原作のインストール）と、上の「無いと動かない」Mod。使う機能に要る Mod（「特定の機能が使えなくなる」の表）。
- Python 3（上の「Mod でない前提」）。ソースからビルドするときだけ、.NET SDK も。
- 原作の場所：`MuseStudio/tools/original_path.txt` に 1 行で書くか、環境変数 `MUSESTUDIO_ORIGINAL` に入れます（どちらもリポジトリには入りません）。
- **リポジトリは浅い場所に置いてください**（例：ドライブの直下の `KK_MuseStudio`）。`game/mods` は原作の `mods` へのリンクなので、深い場所だと Mod のファイルのパスが Windows の 260 文字を超え、Sideloader が Mod を一つも読めません（Mod の部屋・AL の体位・ペニスバンドが無くなり、3 の `no match:` にそれらが並びます）。
- 動いている CharaStudio・コイカツは閉じておきます（2〜4 はゲームを起動します）。

### 順番と、うまくいったかの見分け方

1. 起動用のフォルダを作る。最後に `ready:` と、作ったフォルダが出れば成功です。

   ```bash
   python -B MuseStudio/tools/setup.py
   ```

2. プラグインを入れる。どちらか一つです。

   **ビルド済みを入れる（.NET SDK 不要）**

   - [Releases](https://github.com/mizumori-bit/KK_MuseStudio_alpha/releases) から、**このクローンのコミットと同じ**リリースの `MuseStudio-dll-<タグ>.zip` を落とします。
     - リリースの本文に、対応するコミットがあります。
     - DLL は、そのコミットの `data/` と契約と組で動きます。違うコミットなら、`git checkout <コミット>` で合わせます。
   - zip の SHA-256 は、隣の `.sha256` で確かめられます。
   - 次を実行します。zip の中の各ファイルの SHA-256 と、対応するコミットがこのクローンと同じかを確かめてから、`game/BepInEx/plugins/MuseStudio/` に入れます。
   - `install: MuseStudio … -> …` が出れば成功です。違うコミットの DLL は入れずに理由を出します。

   ```bash
   python -B MuseStudio/tools/install_dll.py MuseStudio-dll-<タグ>.zip
   ```

   **ソースからビルドする（.NET SDK が要る）**

   - `build: …MuseStudio.dll (… bytes, … sources)` と、キャラメイクの部品の `build: …MuseMaker.dll …` の 2 行が出れば成功です。
   - `FAILED` なら失敗で、コンパイラの出力がその上に出ます。

   ```bash
   python -B MuseStudio/tools/build.py
   ```

3. データを作る。原作を一度起動して（窓が開いて閉じます。原作の表を初めて読むので数分かかります。2026-11-05 の新しいクローンでは約 3 分半）、原作の表を読み、`data/` の 5 つのデータと、リポジトリの直下の `for_muse/talk-poses.md`（MUSE_GUIDE 8.7 の資料）を作ります。`wrote …` が並び、最後の `no match:` が `none` なら、全部見つかりました。名前が並ぶときは、その Mod が無いか読めないので、その部屋・体位などは使えません。原作の表そのものは `game/` の中（`studio_lists.json`・`original_lists.json`）にだけ置き、リポジトリには入れません。

   ```bash
   python -B MuseStudio/tools/derive_data.py --dump
   ```

4. 全点検。空きポートに**テスト用のブリッジ**を立て、MuseStudio をそこにつないで流します（Muse が見ているブリッジ、ユーザーのキャラ・設定には触れません）。`CHECK SUMMARY pass=… fail=0` と、続くキャラメイクの分の `fail=0` が出れば成功です。撮った画面と結果は一時フォルダに残ります（最後に場所を表示します）。同じ PC でほかの窓が前に出ると、実クリック・実キーの項目が落ちることがあります（下の「今できること」の「確認」）。

   ```bash
   python -B MuseStudio/tools/run_checks.py
   ```

5. ブリッジの準備（鍵必須のまま。MUSE_GUIDE 7.1）。**Muse がつなぐ前に**、まず経路を決めます。
   - **経路 A（鍵を渡す）**：Muse が本物の鍵を持ち、要求に付けられる環境。Tailscale の中継（`tailscale serve`）を通ります。
   - **経路 B（Muse 専用の受け口）**：Muse の側の代理文字列が tailnet の経路で本物の鍵に置き換わらない環境（作者の PC はこちら）。**本物の鍵は PC の外に出しません**（鍵を表示して渡す手順は踏みません）。

   **両方の経路で**：
   - `bridge/bridge_config.example.json` を `bridge/bridge_config.json` に写し、`allowed_hosts` にこの PC の tailnet の名前を書きます（Muse の要求の `Host`。書かないと tailnet からの要求は `403`）。`auth` は `"required"`（既定）のままにします。`bridge_config.json` は PC ごとの設定で、リポジトリには入りません。
   - ブリッジを一度起動すると、`bridge/cache/tokens.json` に鍵が 2 つ（Muse 用・アプリ用）できます。MuseStudio と起動役は、そこからアプリの鍵を読みます（人手は要りません）。

   **経路 A のとき**：
   - tailnet から届くよう、この PC の Tailscale の中継（`tailscale serve`）をブリッジのポート（既定 `127.0.0.1:18765`）へ向けます。届く機械は tailnet の ACL で絞ります。
   - Muse の鍵を表示し、Muse の安全な入力欄へ入れます（チャットに貼らない）。

     ```bash
     python bridge/bridge.py --print-token muse
     ```

   **経路 B のとき**（MUSE_GUIDE 7.1 の「あなた専用の受け口」）：
   - 機械の確認：`python bridge/bridge.py --list-machines` で tailnet の機械と StableID を表示し、Tailscale の管理画面（Machines）と見比べて Muse の機械を確かめます。
   - 設定：`bridge_config.json` の `muse_listener` に、その StableID（`machine`）と `"enabled": true` を書きます。
   - 届く範囲：Windows のファイアウォールで、そのポート（既定 18767）への受信を、Muse の機械の tailnet の IP と Python だけに許します（管理者の PowerShell の `New-NetFirewallRule`）。tailnet の許可設定（ACL）も、Muse の機械からそのポートだけに絞ります。
   - 動き：ブリッジを起動すると、受け口がこの PC の tailnet の IPv4 アドレスで開きます（`auth` が `"required"` で、Tailscale がこの PC のアドレスを答えるときだけ。IPv4 だけで、全部の口やほかのアドレスでは開きません。受け口の設定に誤りがあっても、ブリッジは鍵必須のまま動き、受け口だけが開きません）。Muse は送り先のポートを 18767 にし、いつもの `Authorization` を付けたまま送ります。
   - Muse の `Authorization` の照合値は、最初の 1 回で覚えます。Muse の側で値が変わったときは、次を実行して覚え直させます（覚えた値のファイルが読めないときも、勝手には覚え直しません）。

     ```bash
     python bridge/bridge.py --forget-muse-placeholder
     ```

   **成功の見分け方**：鍵を付けない `GET http://127.0.0.1:18765/health` が `{"ok": true, "auth": "required"}` だけを返し、Muse が読むと中身（`launch` など）が返ります（経路 A は鍵を付けて、経路 B は受け口から）。

6. 起動。起動役がブリッジ・MuseStudio・Muse のパネルを開きます。`launcher/panel_config.example.json` を `launcher/panel_config.json` に写して、この PC の値を入れます（無ければ例の設定で動きます。`game_mode` は `musestudio`）。成功の見分け方：MuseStudio の窓が開いてキャラを選ぶ画面が出て、`/health` の `launch.phase` が `stage_ready`、選ぶと `character_selected` になります。

   ```bat
   launcher\start.cmd
   ```

ゲームを起動しない軽いテスト（ブリッジ・対戦の通信。標準ライブラリの unittest、対戦の分は `cryptography` があるときだけ）：

```bash
python -B -m unittest discover -s bridge/tests
```

起動役の「ホバーでフォーカス」のテスト（窓の呼び出しを置き換えて流します。Windows のみ）：

```bash
python -B -m unittest discover -s launcher/tests
```

ビルド済みの DLL の入れ方のテスト（zip の中身・SHA-256・コミットの確かめ。ゲームもネットも使いません）：

```bash
python -B -m unittest discover -s MuseStudio/tools/tests
```

## 使い方

- 起動は起動役（上の 6）か、`MuseStudio\game\CharaStudio.exe` です（作業フォルダを `game` にして起動してください）。ブリッジは既定で `http://127.0.0.1:18765` で、プラグインの設定（`game/BepInEx/config/metamuse.musestudio.cfg`）で変えられます。
- **ブリッジの鍵**（2026-11-05、GPT のセキュリティレビュー SEC-01・06。MUSE_GUIDE 7.1）：鍵の作り方・渡し方は上の 5 です。作り直すときは `python bridge/bridge.py --new-tokens`（ブリッジは止めなくてよい。古い鍵は効かなくなり、Muse は渡し直すまでつなげません）の後に表示し直します。`auth` は最初から `"required"`（既定。項目が無くても同じ）で使います。`"off"`（鍵なし）はブリッジのテストのための値で、つなぐ手順では使いません。
- Studio の画面部品は隠しています。F2 で出し入れできます。
- 画面の UI（上の操作の列・キー操作の一覧・在席の表示）は、F3 か、メニューの右上の「UI を隠す」で隠せます。台詞の枠は残ります。もう一度押すと出ます。
- **コーデカード**（PR #46 §3）：「服」のメニューの下の「コーデ（カード）」で、`MuseStudio/game/UserData/coordinate` にあるコーデカードに着替えます（Muse もブロックで同じことができます）。原作の側のフォルダは読みません。原作で作ったカードは、このフォルダへ写すと一覧に出ます。MuseStudio から開いたキャラメイクで保存したコーデは、最初からここに入ります。プレイ中・対戦中・彼女が出かけている間は着替えられません。キャラを切り替えて戻す・起動し直すと、カードの服に戻ります。
- **レッテル**（PR #46 §1）：何用のコーデか（後に部屋も）の説明は、Muse がブリッジの口で書き、`bridge/cache/labels.json`（この PC の手元だけ）に入ります。ユーザーが自分で書く・直すときは、そのファイルで該当の項目の `"by"` を `"user"` にすると、Muse に上書きされません。ブリッジが動いている間に直してもかまいません（ブリッジは読み書きの前にファイルを読み直し、直したものを取り込みます。保存しかけで読めない間は、何も書きません）。
- **持ち物と予算**（PR #46 §7）：パネルの「持ち物」です。
  - **予算**：アプリを起動している 1 時間ごとに 100 入ります（端数は持ち越し）。店で品を買えるのは、あなただけです。
  - **渡す・勧める・使う**：
    - あなたの持ち物は、彼女に「渡す」（彼女が受け取れば移ります）、「棚へ」置く、彼女に「勧める」（使うかは彼女が決めます）、自分で「使う」ことができます。
    - 棚（家のもの）は二人で使います。彼女からの申し出は「受け取る／断る」で答えます。
  - **効き目**：品は彼女の気分（酩酊・尿意・発情）だけを動かします。重ねると効きが鈍り、等級の上限で止まります。酔うと頬が赤くなり、目が少し細くなり、会話では視線が少しゆらぎます（`data/stage.json` の `gaze_sway_degrees`）。
  - **品と値段**：品と値段は `data/items.json`、入る額は `data/rewards.json` で変えられます。
  - **設定**（F1 の「持ち物」）：「予算を Muse に知らせる」（既定は切）と「Muse があなたに品を使う」（既定は入）。
- **部屋の自動登録**（PR #46 §4.1）：起動時に Studio のマップ（原作と Mod）を全部、名前だけ登録します。「場所」のメニューは今までどおり、いつもの部屋（「最初から並べて置く部屋」）が出ます。「全部の部屋（N）」を押すと、いつもの部屋を先頭に、ほかの部屋が並びます（手で整えた部屋、原作の部屋、Mod の部屋の順）。ほかの部屋は、行くときに読み込みます（1 部屋 0.2〜1 秒ほど）。行った部屋は、設定（F1）の「舞台」の「読み込んだまま置く部屋の数」（既定 6）まで読み込んだまま置き、超えると使っていない部屋から外します。H の場所の種類は、その部屋を初めて読み込んだときに取り、`game/UserData/MuseStudio/rooms.json` に覚えます。H の場所の無い部屋は、その場だけで使えます。そうした部屋の立ち位置やプレイの位置は、「この部屋の位置を調整」で直せます。
- **口の動き**（PR #46 §6）：セリフを話す速さ（1 秒に 8 拍ほど、「、」「。」で一拍）で出し、話している人の口を開け閉めします。Muse がルビ `漢字《かんじ》` を付けていればその読みで、無い漢字は 1 字 2 拍です（台詞枠には読みを除いた形が出ます）。画面を押すと全文が出て口は止まり、表情の口に戻ります。口の形は表情のままで、開き具合だけが表情の上限の中で動きます。動かし方は原作が声に合わせて口を動かすのと同じです（声の大きさのように、音のあいだで閉じきらずに沈み、開くのは速く閉じるのはゆっくり）。キス・口での奉仕の間は動きません。設定（F1）の「舞台」の「口の動き」を切にすると、今までどおりセリフはすぐ出ます。速さと間、口の開きの大きさ（`voice_peak`・`voice_dip`）は `data/stage.json` の `speech` で変えられます。
- **時計**（PR #46 §8）：在席の表示の下に、この PC の今の時刻を出します。設定（F1）の「舞台」の「時計を出す」で消せます（既定は出す）。UI を隠すと、時計も隠れます。
- カメラを自分で動かすと（ドラッグ・ホイール・キー）、止まったところで部屋ごとに覚えます（`game/UserData/MuseStudio/cameras.json`）。次の起動と、その部屋にまた入ったときは、その位置・向きから始まります。Muse がブロックでカメラを指定したときは、そちらが優先です。プレイ中・対戦中のカメラは覚えません。
- **部屋の位置の調整**（ユーザーの要望、PR #11・PR #23）：「場所」のメニューの「この部屋の位置を調整」で、部屋の位置の基準を直せます。上のボタンで種類を選ぶと、その種類の印（円と向きの矢印と細い柱、家具の陰でも見えます）だけが種類ごとの色で出ます。種類は、**プレイ位置**（原作の H の場所：床・壁・椅子など）・**行動の位置**（その部屋のお出かけ：トイレ・シャワー・ひとりで・着替え）・**立ち位置**（その場）・**近付く**（「近付く」の行き先）です。印をドラッグで床の上を動かし、下の枠で細かい移動・向き・高さを直します。変えるたびに保存され（`game/UserData/MuseStudio/spots.json`）、プレイ・お出かけ・近付くが直した位置で行われます。「近付く」は、行き先を置かなければ今までどおりカメラに向かって歩き、置いた部屋ではそこまで歩いて印の向きを向きます（家具を通り抜けるときの直し方）。モーションと家具の位置が合わないとき（トイレットペーパーなど）の直し方にもなります。
  - **プレイ位置の種類**（PR #46 §4.2）：プレイ位置では、その部屋にある種類（床・ベッド、椅子、壁など）のボタンが並び、選んだ種類の印だけが出ます（開いたときは最初の種類。「全部」で全部）。いくつかの種類で使う位置は 1 つのままで、どの種類を選んでも同じ印です（動かすと、どの種類でも動いています）。
  - **位置の 3 つの層**：原作の位置（初期値）・保存したデフォルト・今の位置です。「今の位置をデフォルトにする」で今の位置を覚え、「デフォルトに戻す」でそこへ戻ります。「初期化（原作の位置へ）」は初期値に戻し、保存したデフォルトは残ります（あとで「デフォルトに戻す」で戻せます）。デフォルトを消すときは、初期化してから「今の位置をデフォルトにする」を押します。印の名前の横に「調整済み」「デフォルトあり」「デフォルトの位置」が出ます。
  - **編集したものだけ**：「編集したものだけ：入」で、今の位置かデフォルトを保存した記録のある印だけが出ます（手で元の場所へ戻しても、初期化するまでは編集したものです）。
- **初期値に戻す**（PR #23）：設定（F1）の「舞台」に「カメラの記憶を初期値に戻す」「位置の調整を初期値に戻す」があり、2 回押すと全部の部屋の分を消します。位置の調整では、保存したデフォルトは残ります。
- 新しい Mod を入れたときも、上の `derive_data.py --dump` をもう一度実行します（原作を読み直して、5 つのデータを作り直します）。
- 並べた部屋の配置（家具の位置、H の場所）を調べるときは `python -B MuseStudio/tools/run_checks.py --probe <場所のキー> --keep`。自己チェックと同じく切り離した環境で、部屋の模型の一覧・H の場所・上と四方からの画像・彼女のアクセサリを、一時フォルダに書き出します。

## 今できること

- **起動**：起動役（`launcher/start.cmd`）が Godot 版の代わりに MuseStudio を起動します（`launcher/panel_config.json` の `game_mode` が `musestudio`。無ければ `panel_config.example.json` の設定で動きます。窓は最大化）。
  - 専用フォルダから Studio が起動します。目覚めた時点でブリッジに起動の開始を知らせます（`/health` の `launch`：`app_starting`→`stage_ready`→`character_selected`）。
  - 設定の部屋（既定：自室・女の子の部屋・浴室・家のトイレ・ベッドルーム）を最初に全部シーンへ並べて読み込みます（約 1 秒、メモリ +230 MB）。部屋の間の移動は一瞬です。

- **パッケージ**：セリフ枠（名札・本文。`sound` ブロックは別の書体）で表示します。文字送りで出て、長いセリフは枠が上に伸び、左下の Muse のパネルを避けます。進めるのはクリック・Enter・Space（最初の一押しで全文）、自動送りは枠の右上で切り替えます。モーションの切り替えは重ね合わせでなめらかにつながります。
  - ブロックの各項目：感情ラベル → 原作の表情（どの表情も秒数で、その場面の既定の表情へひとりでに戻る。`faces.json` の `return`）、シーンキー → Studio のモーション（強度は `#n` の指定か速さ）、カメラ → 4 つの位置、場所 → マップを読み込んでから表示、プレイ → ペース・速さ・入れる・抜く・ゴム・フィニッシュ、ユーザーがチャットで頼んだときの開始・変更（`play.start` に `request`・`basis`・`location`。アプリが起動・キャラ・依頼の重なり・番号・場所・可否・スポットを確かめ直す）、気分 → 満たされた・トイレに行った・漏らした、行動 → 自慰・トイレ・シャワー・一緒にシャワー、彼女の思い（`belief`）。

  - パッケージの印 `launch`・`character` が今の起動・キャラと違えば捨てます。独り言（`monologue`）は 10〜20 秒ごとにひとりでに進み、ユーザーが戻る・Muse が返事をする・場所や気分の段階が変わると残りを捨てます。
  - `approach` は実際に歩いて近づき（家具の手前で止まる。足音付き）、`lean_in` は上体を前に傾けます。
  - 知らない感情ラベルは標準の表情に、知らないシーン・カメラ・場所はそのままにして、表示を続けます（イベントは出しません。MUSE_GUIDE 第 4 節）。項目の値が今は使えないとき（着ていない服、残していない部屋など）は `block_refused` で伝えます。

  - ふたなりの属性は、カードのアンセンサー（原作のキャラメイクの「陰茎の表示」）か `stage.json` で決まります。
- **おさわり**：彼女の上ではカーソルが原作の手になります（愛撫の間は、原作どおり部位と道具のアイコン）。F4 で当たりの形を色付きで見せます。プレイの外で胸・股間・お尻を長押しするか撫でると、その場で立ち愛撫が始まります。マウスで彼女に触れます（骨に付けた見えない当たり。頭・頬・手・腕・胸・お腹・お尻・股間・アナル・太もも・脚）。

  - 愛撫のプレイでは原作の手・指・舌・電マ・バイブ（HandCtrl の部品と層）が彼女の体に付きます。奉仕と挿入の間も、原作の体位ごとの表のとおりに使えます（挿入で入っている間の股間は不可）。押すとクリック、押したままでドラッグ（マウスの動きの値は原作の `HandCtrl` と同じく、ゆっくり動いて円の中に収まる）、部位の上でホイールで道具を替え、右クリック・「外す」で外します。顔を押すとキス（原作のキスのカメラ）。

  - プレイの枠に、体位・場所・どちらが主導か・ペース・ゲージが出ます。動きは原作どおり、混ぜ具合が数秒ごとに揺らぎます。

  - 男性の体の身長は、設定の「あなたの体の身長」（0.35〜0.85。原作の男性は 0.6 固定で、キャラメイクに欄がありません）。
  - 場所は、その場（立っている所）と、その場所の原作の H ポイントです。体位ごとに使える場所だけ出ます。
  - AnimationLoader の Mod の体位 135（奉仕 65・挿入 70）も、プレイのメニューの「奉仕＋」「挿入＋」から選べます（名前は日本語に訳しています）。速さは原作の最高速度（挿入 3.0・奉仕 2.5・愛撫 1.5）で止まります。
  - Godot 版の 80 のプレイが、Studio の H のモーション（原作の H の状態ごと）と、原作の H の一覧の行に結び付いています。体位の服・カメラ・置く位置のずれは原作の値です。カメラは壁や家具の手前に寄せます。
  - 誰が何をするか（役割・使う部位・必要な体）は Godot 版の決まりのとおりです。攻守交代では彼女が原作の男性側を演じ、ペニスが無ければ Mod のペニスバンドを着けます。アナルは原作のアナルの動きのある 8 つの体位で選べます。
  - 挿入は抜けた状態で始まり、Muse の `insert` か、ペース 1 以上で入れます。ゴムは入れる前に決まっている必要があります（設定で「毎回 Muse が聞く／いつも付ける／いつも付けない」）。
  - ペースは Muse が決めます（枠は表示だけ）。押さない・Muse が話さない状態が 45 秒続くと止まります。
  - 「目線へ」で相手の目の位置から見られます。「あなたの服」で相手の体の服を替えます（`player_clothes_changed`）。
  - 体位中の彼女と相手の視線・首は、原作の体位ごとの目線の表のとおりに動きます。手足は原作のモーション IK で相手に合わせ、男性側を演じる体は身長の違いを腰の位置で合わせます。
- **ゲージと絶頂**（Godot 版の作りを移植）
  - 彼女の快感度ゲージが、おさわり・シーン・プレイのペースで上がります。節目（`gauge_milestone`）と絶頂（`climax`）を Muse に伝え、絶頂の顔と余韻の顔をします。
  - 彼女のゲージが 1 になると、彼女の絶頂の動きをします。射精は宣言です（`soon` で待ち、場所で原作のフィニッシュ）。彼女のゲージが高いときは同時に絶頂します。
  - 液は原作の体位ごとの汁の表のとおりに付き、外に出すと原作の粒子の液が飛びます。中出しの後に抜くと液が垂れ、口に出した後は吐き出します（ゴムがあれば出ません）。漏らしたときは原作のおしっこの粒子が出ます（立った姿勢ではごく薄い）。
- **気分と欲求**：発情・尿意・シャワーの気持ちのゲージ（シャワーの気持ちはプレイの後と、Muse が「掃除などで動いた」と送ったときに溜まる）（性格や時間・おさわり・プレイで変わる。閉じている間の分も足す）。段階が変わると `mood_changed`。発情・尿意が目安を超えたとき、シャワーの時刻（実時刻 21:30〜3:00）か、シャワーの気持ちが目安を超えたときは、勝手に行動せず Muse に `urge` で知らせ、状態の `urges` に載せて 10 分ごとに知らせ直します（`data/urges.json`）。
- **行動とお出かけ**：Muse のブロックの `action` で、自慰（いちばん近い場所で。絶頂で終わる）、トイレ・シャワー（彼女がひとりで部屋へ行き、原作の覗き用の動きをして戻る。カメラは残る）、一緒にシャワー（ふたりで浴室へ、裸で立ってするプレイ）をします。後を追うと見られずに覗けます（パネルの「声をかける」を押すまで見つかりません。気づかれていないので、彼女の目も顔もこちらを向きません。出るときにユーザーがいれば Muse に伝わります）。
- **在席**：左上の「在席／離席」。Muse には彼女が知り得る形で伝わります（同じ部屋にいるとき、または会った時点）。
- **拍の材料**：アプリは拍を求めません（B 案）。状態の `beat` に、最後のパッケージを出し終えてからの秒数と、問いの頃合いを載せます。
- **効果音**：H の効果音は原作の仕組み（体位ごとの効果音の表）で鳴ります。場所を移るとドアの音（原作の選び方：学校の部屋は引き戸、ほかは開き戸、外へ出るときは出た部屋のドアを閉める音、ドアの無い場所どうしは無し）、原作に環境音のあるマップでは環境音、歩くと足音、愛撫の道具の音。
- **ひとりの時間・着替え**（2026-11-04）：彼女が自分の部屋（女の子の部屋）へひとりで行くことがあります（ひとりで過ごす・自慰・着替え。どれかは覗かないと分かりません）。発情が高いと頬が赤くなります。出かけている間は、ユーザーがどこへ行ったかは Muse に伝わりません。
