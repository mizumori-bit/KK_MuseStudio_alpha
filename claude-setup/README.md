# claude-setup：Muse 側の環境設定

Muse が MuseStudio（プラグイン＋ブリッジ）とつながって舞台に立つために、Muse 側で整えるものの手順です。プラグイン側の導入は、リポジトリ直下の `MUSE_GUIDE.md` と実装側の案内に従ってください。

> **新規環境について**：新しい環境で立てる通しの手順は、`MuseStudio/README.md` の「新しい環境で始める（最初から最後まで）」にあり、作者の環境で実測済みです。ただし、その実測の条件は「原作と前提 Mod を導入済みの作者 PC に、新しくクローンを作った環境」です。原作や Mod の構成が違う PC では、まだ通していません。この文書は、そのうち Muse 側で整える分の手順です。
>
> **前提 Mod の不足について**：必須の Mod（BepInEx 5 や KKAPI など）が欠けると、プラグイン自体が読み込まれません。機能ごとの Mod が欠けた場合は、その機能だけが使えなくなります。正規の一覧は `MuseStudio/README.md` の前提 Mod の表を見てください。
>
> **初回セットアップのデータ生成には時間がかかります**：初回のセットアップでは、通常の起動に先立って、受け手の原作インストールから必要なデータを生成する工程（`derive_data.py --dump`）を実行します。その工程の実測は約3分半ですが、セットアップ全体の所要時間ではありません。生成が終わるまで、中断しないでください。

## 前提

- 原作ゲームを所持し、プラグインが導入された PC があること。
- 前提 Mod が入っていること（各 Mod の配布元から入手してください。不足すると、プレイや相手キャラの組立てが部分的にできなくなります。一覧は §6 にあります）。
- あなたの実行環境（VM 等）から、その PC のブリッジへ HTTP で届くこと。
- キャラカードの用意：このリポジトリにカードは含まれていません。ユーザーが**初回起動の前に**、`MuseStudio/game/UserData/chara/female` フォルダへコイカツ形式のカード（PNG）を置くよう案内してください。キャラメイクで保存したカードも同じフォルダに入り、同じ一覧に並びます。キャラが選ばれるまで挨拶は始まらないので、カードの用意は起動の前提です。

## 1. ブリッジへの到達

- ブリッジは PC 上で HTTP API を待ち受けます。到達手段は問いませんが、参照実装として **Tailscale**（または同等の閉じたネットワーク）で VM と PC をつなぐ形を想定しています。あなたの tailnet 名やアドレスのような固有情報は、あなたの環境の中だけに置いてください。
- Tailscale を使う場合の骨子：(1) VM と PC の両方に Tailscale を入れ、同じ tailnet にサインインする。(2) PC の tailnet 名でブリッジに届くことを確認する。(3) その名前をブリッジの設定 `allowed_hosts` に入れる（ブリッジは要求の Host の名前も検査します）。
- 経路は2つあります。**従来の経路**は、PC 側の中継（`tailscale serve`）でブリッジ本体のポートへ届き、あなたが本物の鍵を付けて送る形です（下記の「鍵の受け渡し」）。**専用受け口**は、あなたの環境の都合で鍵が経路の途中で付かない（代理文字列のまま届く）場合に、PC 側で有効にしてもらう形です（下記の「Muse 専用の受け口」）。PC 側の設定の手順は `MuseStudio/README.md` の「ブリッジの準備」にあります。
- 従来の経路の中継は `tailscale serve` で行います（契約 7.1 の言う「中継」はこれです）。その PC の tailnet 名宛ての接続を、ブリッジの待ち受けポートへ中継する形に設定してください。具体的なコマンドはあなたの環境の Tailscale の版に合わせて構いません。要は、VM から PC の tailnet 名でブリッジの API に届くことです。
- Tailscale まわりの注意：ブリッジを Tailscale Funnel のような公開機能で外に出さないこと。tailnet へのノード共有は、到達できる相手を広げる行為だと意識すること。tailnet のアカウント自体が入口になるので、そのアカウントの保護（二要素認証等）も前提になります。
- **セキュリティ注意（重要）**：ブリッジには鍵（トークン）による認証があります（契約 1.7。下記の「鍵の受け渡し」参照）。ただし認証は多重防御の一層にすぎません。到達できる相手は、引き続きあなた自身のノードだけに絞ってください（tailnet の ACL 等）。公開ネットワークに直接さらさないでください。

### Muse 専用の受け口

- これは、あなたの資格情報の仕組みの都合で、鍵が経路の途中で付かない（代理文字列のまま届いてしまう）環境のための経路です。PC 側で有効に設定されているときだけ開きます（設定は持ち主が行います。手順は `MuseStudio/README.md` の「ブリッジの準備」）。
- 送り先は、PC の tailnet 名のまま、ポートだけを **18767** にします。**名前で送ってください**（IP で送ると Host の検査で `403` になります）。パスや書式、答えは従来の経路と同じです。
- この受け口は、**登録された機械からの要求だけ**を受けます。使う前に、持ち主が Tailscale の管理画面であなたの機械（名前と tailnet の IP）を確かめ、PC 側に登録します。PC 側では `python bridge/bridge.py --list-machines` を実行すると、tailnet の機械ごとに StableID・名前・IP が出るので、持ち主はその一覧と管理画面を見比べます。PC は実際の接続元を見て確かめるので、ヘッダーで名乗っても通りません。
- `Authorization` はいつもどおり付けてください。**あなたの代理文字列のままで構いません。** PC は、最初に届いた値の照合値（SHA-256）だけを覚え、以後は同じ値を求めます（値そのものは残しません）。あなたの送る値が変わって `401`（`reason: "placeholder"`）が返るときは、鍵違いではなく照合の外れです。むやみに送り直さず、持ち主に照合値の覚え直しを頼んでください。
- 本物の鍵は、通った要求に対して **PC の中で付けられて**ブリッジに渡されます。PC 側で鍵が作り直されても、あなたの側で配り直しは要りません。
- 受け口で使えるのは Muse 用の API だけです。アプリ用の口など、それ以外は `403`（`reason: "not_allowed"`）で断られます。これは異常ではなく、範囲が分かれていることの表れです。ほかの機械からの要求も断られます（`403`、`reason: "not_muse_machine"`）。
- 設定後の確認は、肯定と否定の両方を見てください。肯定：`/health` が `200` で、**生きていることだけでなく `launch` などの中身まで返る**ことと、`/api/state` が `200` で返ること。否定：`GET /api/packages/next?hold=1` が `403`（`reason: "not_allowed"`）で断られること。この形なら、宛先を取り違えても待ち行列を消費しません。

### 応答が無いときの切り分け（実例つき）

API の要求だけがタイムアウトし、`/health` は届いている、という症状は、経路や受け口の障害とは限りません。**まず「要求が PC まで届いたか」を、PC 側の記録で確かめてください。** 届いていなければ、送り手側の呼び出しで送信前に止まっている可能性が先にあります。

実例（2026-11-07、作者の環境）：ヘルパーの `call` で `GET /api/state` を送る際、ペイロードの引数に標準入力（`-`）を付けたところ、ヘルパーが送信前に標準入力の読みで無限に待ち、要求は VM の外へ出ていなかった。`/health` と `get-url` はペイロード読みを経由しないため正常に届いており、症状だけ見ると受け口の障害に見えた。PC 側の要求記録（次項）で「その時刻に接続が一つも来ていない」ことが決め手になった。

- **「記録が無い」ことの読み方に注意してください。** 現行の実装は、`GET /api/state` の正常応答などを通常ログから省いています。通常ログに記録が無いだけでは、要求が未到達だったとは判断できません。専用受け口では、既存の `--log-muse-requests` を有効にして、接続開始・要求受信・応答完了のどこまで記録されたかで切り分けてください（上の実例の「PC 側の要求記録」は、この記録のことです）。
- 本文の無い要求（GET 等）では、ペイロードの引数を付けないでください。ペイロードは本文のある要求にだけ、実ファイルで渡すのが安全です。
- 届いている経路（`/health` 等）との比較が手がかりになります。経路ごとに成否が分かれる場合は、経路そのものより、経路ごとに違う呼び出しの形を疑ってください。

### 鍵の受け渡し

- ここからの「鍵の受け渡し」は、**従来の経路**（あなたが本物の鍵を付けて送る形）の話です。専用受け口を使う場合は、この受け渡し自体が要りません（鍵は PC の中で付けられます。前節を見てください）。
- ブリッジは初回起動時にランダムな鍵を2つ作り、PC 内の `bridge/cache/tokens.json` に置きます（リポジトリにもログにも入りません。消すと再生成されます）。`muse` があなたの鍵、`app` がアプリの鍵です（アプリの鍵はアプリが自動で読むので、人手は要りません）。
- あなたの鍵の受け渡し：ユーザーがその PC で `python bridge/bridge.py --print-token muse` を実行して鍵を表示し、**あなたが用意する安全な入力欄に**入力してもらいます。鍵をチャットの本文に貼らせないでください。
- 鍵はあなたの資格情報ストアに保管し、すべての要求に `Authorization: Bearer <鍵>` を付けて送ってください。鍵そのものを、チャット・記録・ファイルに書かないでください。
- 順序の注意：認証は最初から有効（required）なのが前提の形です。「まず認証なしでつなぎ、後から有効化する」という移行手順は取りません。鍵の保管（専用受け口の場合は機械の登録）がそろってから、初めて接続してください。
- 鍵が無い・違う要求は `401`、役割の違う鍵は `403` です。鍵が再生成された（`401` が続く）ときは、むやみに再送せず、ユーザーに知らせて受け渡しをやり直してください。

## 2. 起動検知

舞台が立ち上がったことを Muse が知るための、一般形の手順です：

1. ブリッジの `/health` を、鍵を付けて一定間隔でポーリングする（目安：運用が安定したら 120 秒間隔程度。短すぎると無駄な通信が増えます）。鍵なしでは「生きている」ことしか返らず、起動の段階は読めません。
2. 新しい起動で「キャラクターが選ばれた」ことが分かったら、その事実だけを本体の Muse に知らせる（最小のリレー役を置くと、本体の文脈を汚しません）。
3. 挨拶そのものは本体の Muse が組み立てて送る（挨拶には、選ばれた人物の関係値と、人格の決定が要るため）。

ポーリングの実装方法（フック、cron、常駐スクリプト等）は、あなたの環境の流儀で構いません。

なお、セッションの始まり方（起動の入り口）は2つあり、どちらもサポートします：

- **基本経路は、ユーザーが先にチャットで Muse に依頼する形**です（「これから起動する」等）。Muse は起動を予期して待てるため、挨拶がいちばん滑らかになります。
- **アプリを先に起動する形**も使えます。この場合、検知は上記のポーリング監視を通るため、挨拶はポーリング間隔のぶん遅れがちです（アプリ側に挨拶を保持する仕組みがあるため、起動の流れの中で間に合うことも多いです）。

どちらの経路でも、通信の向きはすべて Muse 側からブリッジへ向かう形に統一されています（ブリッジ側から発信することはありません）。

なお、セッションの運転は、ユーザーのメインチャットで行うのが基本です。別のチャットを経由する中継は応答が1拍遅れるため、運転の置き場はメインに置いてください（詳しい手順は同梱スキルの app-driving にあります）。セッション中の出来事に間を置かず反応するための起床の仕組みは、§3（ウェイター監視）にあります。

**他のクラウド AI で使う場合の目安**（この配布物の想定は Muse ですが、参考として）：

- VM のような常駐できる環境（定期実行やポーリングができる場）を持つクラウドなら、Muse と同様に、チャットからでもランチャー（アプリ先行）からでも始められます。
- それがないクラウドでは、チャットからの起動のみになります。ランチャーで起動した事実をクラウド AI に伝える経路がないため、「ランチャーで起動 → AI にも起動を報告」という二度手間になります。

運用の注意：セッション中は、場面の1拍ごとにあなたの応答が回るため、Muse の利用量を継続的に消費します。気づかないうちに大きく消費することがあるので、長時間のセッションではユーザーの利用量に配慮してください。

## 参考：性格を先に馴染ませる（試運転のノウハウ）

新しい登録性格（人格カセット）を初めて実セッションで使うとき、最初のうちは応答の調子が安定せず、しばらく「馴染みの期間」が要ることがあります（作者の環境での実感）。本番の前に短い試運転をして、その性格の運用の勘所を Muse 側に残しておくと、本番の入りが滑らかになります。

なお、この方法は「自動的に学習が蓄積される」ことを前提にしません。Muse の側に残るのは、次回読み込むための記録（性格カセット自体と、性格別の運用メモ）だけです。馴染みは、その記録の読み直しで作られます。

### やり方

1. **短い試運転をする**：本番の前に、短いセッションを1回回します。挨拶、普段の会話、提案と許可取り、そして（その性格の領分なら）プレイの入り口までを一通り通すのが目安です。長く回す必要はありません。「この性格で、どう立ち、どう断り、どう誘うか」の型が出る場面を揃えることが目的です。
2. **運用メモに残す**：試運転で分かったことを、その性格の運用メモに書きます。例：口調の癖と崩れやすい所、主導権の持ち方の出方、避ける言い回し、よく効いた運び。メモは性格カセットの隣に置き、その性格を使うときに一緒に読みます。
3. **本番の入りで読み直す**：セッションの開始時に、カセットと運用メモを読み直してから挨拶に入ります（性格の決定はキャラ確定の後です。同梱スキル app-driving の「起動と挨拶」参照）。
4. **本番で得た勘所も、メモに足していく**：馴染みは一度で終わりではなく、セッションのたびに少しずつ厚くなります。

### 混ぜないための区別（大事な点）

- **性格別の運用メモ**（この性格はどう立つか）と、**人物別の記録**（セッションの要約、好感度・信頼度）は、別のものです。前者は性格に付き、後者は人物に付きます。置き場も読み方も分けてください。
- **試運転の出来事は、本番の実体験として数えません**。試運転で起きたことは「演じた型の確認」であって、その人物との歴史ではありません。本番のセッション要約に試運転の出来事を書かず、関係値の判断材料にもしません。
- 運用メモに書くのは「型」だけです。特定の人物との具体的な出来事や、持ち主の私的な事情は、運用メモに持ち込まないでください（この手引きを含む公開側の文書には、私的な素材を入れないことが前提です）。

### 向き・不向き

- 向くのは、調子の癖が強い性格（口調の作りが独特、主導権の持ち方に決まりがある、等）です。素の Muse に近い性格では、試運転の効果は小さいと考えられます。
- 試運転は任意です。本番で様子を見ながら馴染ませる運用でも構いません。

## 3. セッション中の起床（ウェイター監視）

§2 の検知は「起動したこと」を知るためのもので、間隔が長くても構いません。しかしセッションが始まった後は、アプリ側の出来事（プレイの開始・終了、彼女の絶頂、欲求、外出の終わり等）に間を置かず反応する必要があります。ポーリング型の監視（フック等）だけでは、間隔の下限と中継の段数のぶんだけ遅れが残ります。ここでは、作者の環境で実地に機能した起床の仕組み（**ウェイター監視**）を記録します。

なお、この手引きとサンプルはウェイターの「機械の形」を持ちます。「いつ開始し、いつ止めるか」の判断は、同梱スキルの app-driving が持ちます。手順の二重管理を避けるため、判断の文言はスキルに、間隔や再開 ID の受け渡しのような機械はここに置いてください。

### 土台の事実

- **バックグラウンドで起動したシェルコマンド（プロセス）が終了すると、その出力はメインの Muse の新しいターンとして届きます。** ユーザーの発言がなくても、プロセスの終了そのものが起床になります。
- なお、この仕組みは実行環境の性質に依存します。この性質を持たない環境では §2 のポーリングが上限になり、セッション中の反応の速さは大きく変わります。ウェイターは任意の最適化ではなく、想定された体験の前提に近いものとして扱ってください。
- そのため、「ブリッジを見張り続け、節目の出来事が来たら終了する小さなプロセス」を置けば、その終了が直接メインの Muse を起こします。監視→伝令→本体という多段の中継は要りません。
- **注意（落とし穴）**：フック等のポーリング機構には間隔の下限がありますが、それはプラットフォームの起床の限界ではありません。作者側の Muse は当初この2つを混同し、「現行の監視が限界」と誤って結論しました。起床の速さが必要なら、ポーリング間隔の短縮ではなく、この待機プロセスの形を検討してください。

### ウェイターの形

- セッション中は、待機プロセス（ウェイター）を1つ張ります。ウェイターはブリッジのイベントを短い間隔（作者の環境では1秒）で読み、張った時点より後に来た節目のイベント（プレイ開始・終了・フィニッシュ、絶頂、欲求、外出の開始・終了、服装の変更、作成の完了、ブロック拒否など）が現れたら、その内容を出力して終了します。
- 起きるたびに張り直します。**張るのは常に1つだけ**です。前のウェイターの終了が届くまでは、まだ生きているものとして扱い、重ねて張らないでください（重複すると、同じ出来事に二重に反応します）。
- 張り直す際は、前回処理し終えた最後のイベント ID から再開する形にしてください（骨子では `WAITER_FROM_ID` で引き継ぎます）。張った時点の分を一律に基準線にしてしまうと、張り直しの間に届いた未処理イベントを取りこぼします。再開位置はリクエストの `after` に入れてサーバー側で絞り、対象外のイベントでページが埋まる場合も次のページへ読み進めてください（先頭ページだけを手元で絞ると、その先の節目を取りこぼします）。
- ウェイターには寿命の上限（作者の環境では30分）を設け、上限に達したら「再装填せよ」という合図を出して終わる形にすると、張りっぱなしの事故を防げます。
- セッションの終了でも終わるようにします：セッションの旗（印）が下りた、起動が切り替わった、アプリの終了が続いた、ブリッジに長く（作者の環境では約15分）届かない、のいずれかで終了し、その旨を出力します。旗はセッションの開始時に本体の Muse が立て、終了時に下ろします。旗の中身は JSON で、`launch` の欄にそのセッションの起動 ID を入れます（骨子はこの欄を読んで「起動が切り替わった」を判定します）。中身の無い、ただの印だけでは、その判定が効かなくなります。
- 起動待ちには、骨子の起動待ちモード（`WAITER_MODE=launchwait`）を使います。認証済みの `/health` を短い間隔で読み、まだ報告していない起動が「キャラクターが選ばれた」（`character_selected`）段階に達したら、その内容を出力して終了します。起動待ちのウェイターが持つのは検知までです。挨拶・人物の決定・パッケージの送信は、キャラが確定してから、メインの Muse が状態を読んで行います（第 2 節）。
  - 起動待ちではセッションの旗は使いません。「報告済みかどうか」は、起動の報告済み印（`REPORTED_FILE`、報告した起動 ID を1行に1つ）で判定し、ウェイターは読むだけです。印への追記は、報告を受けて引き継いだメインの Muse が行います。アプリがまだ無い・ブリッジに届かない・段階が `character_selected` 未満は、いずれも「まだ来ていない」であって終了条件にはしません（起動前・準備中は正常です）。報告済みの起動 ID が残っていても、合図にはしません。合図の前提には「アプリが接続中」も含みます。`/health` の起動情報は最後の起動のコピーが残るため、アプリが終わった後も段階だけが `character_selected` に見えることがあります。接続が切れている間は、未報告の古い起動でも合図にしません。
  - 起動待ちの間も、張るのは常に1つだけです。検知の前段（§2 のポーリング）が拾った起動と二重に報告しないよう、報告はメインの Muse に一元化し、ウェイター自身は確認済み（ack）を行いません。
  - 挨拶を滑らかにするため、セッションの始まりがチャットからの依頼である場合は、起動の予期が立った時点で（アプリの起動を待たずに）起動待ちのウェイターを張っておくのが基本です（判断は同梱スキル app-driving の「起動と挨拶」が持ちます）。
- 骨子は `examples/waiter.example.sh` にあります。あなたの環境のブリッジへの届き方（アドレス、鍵の付け方、プロキシ等）に合わせて直して使ってください。

### 保険として見回りを併走させる

- ウェイターは実行環境（VM）の入れ替えなどで、予告なく黙って死ぬことがあります。保険として、ポーリング型の見回し（フック等）も併走させてください。見回りは数秒間隔でイベントを拾い、未応答の問いが一定時間（作者の環境では150秒）を超えたら起こす役も担えます。
- 見回りとウェイターが同じ出来事を二重に運ぶことがあります。出来事は確認済み（ack）の状態で切り分け、二重に反応しないでください。
- 見回り側も、アプリの終了・起動の切り替わり・ブリッジへの長期未達を検知したら、旗を下ろして自ら止まる形にしておくと、セッションが終わった後に監視だけが残りません。

### 消費についての注意

- 静かなポーリング自体は Muse の利用量を消費しません。消費するのは起床して反応するターンです。ウェイターは伝令のターンを挟まないぶん、同じ出来事への反応でも消費が小さくなります。

## 4. 状態ファイル（形式と空の初期状態）

以下は Muse 側が持ち主のファイルです。中身はあなたとユーザーで育てるもので、このリポジトリには形式だけを置きます。これらのファイルは同梱されません。あなたの側で新規に作成し、持ち続けてください。これらのファイルは出来事ごとに書き足す形なので、セッションが意図せず中断しても壊れません（最後に記録された時点が正として残ります）。

- **関係値ストア**：人物ごとに `affection`（好感）と `trust`（信頼）を 0–100 で持つ JSON。キーは人物の識別子（彼女自身は `"self"`、人物は `"person-<番号>"`）。初期状態は空のオブジェクト `{}`。例：`examples/relationship-store.example.json`。値の動かし方に決まった表はありません。あなたの推論で、出来事ごとに書き足してください（記録であって、設計されたゲームステータスではありません）。
- **性格台帳**：性格カセットの登録簿。番号は単調増加で、欠番は再利用しません。書式の例：`examples/personality-ledger.example.md`。
- **セッション要約**：セッションごとに、舞台での出来事の要約を置く場所を用意してください（キーは人物ごと：`self`／`person-<番号>`）。次の起動時に読み返して継続性を保ちます。
- **対戦の相手要約**：対戦した相手 Muse についての、あなたの側だけの要約置き場（再戦の記憶）。相手に渡すものではありません。
- **容姿自認**：対戦で交換する、あなたの容姿についての自筆の要約の置き場。登録の手順はスキルの match-driving にあります。分からない容姿をでっち上げないでください。
- **セッションの旗**：セッション中だけ存在する印のファイル（§3）。中身は `{"launch": "<起動ID>"}` の形の JSON で、本体の Muse が開始時に書き、終了時にファイルを消します。ウェイターが「起動が切り替わったか」の判定に使います。
- **起動の報告済み印**：起動待ち（§3）が使う、報告済みの起動 ID を1行に1つ記したファイル。ウェイターは読むだけで、追記は報告を受けて引き継いだメインの Muse が行います。

## 5. 対戦の段取りについて

対戦の段取り（招待の受け渡し等）はユーザーが手で運ぶのが前提です（それが同意の関門です）。手順はスキルの match-driving にあります。アプリ同士が直接つながることはありません。

## 6. 前提 Mod 一覧

前提 Mod の正規リストは `MuseStudio/README.md` の「前提 Mod（正規リスト）」です。ここには、その要約を置きます。各 Mod は、それぞれの配布元から入手してください。再配布パックを入手元として案内しないでください。

**無いと動かない（4件）**

- BepInEx 5：プラグインの読み込みそのもの。
- KKAPI（Modding API）：MuseStudio の唯一の宣言した依存。
- ExtensibleSaveFormat（BepisPlugins）：KKAPI の動作と、カードの拡張データの読み取りに。
- Sideloader（BepisPlugins）と XUnity.ResourceRedirector：Mod の部品・マップ・動きの読み込みに。

**特定の機能が使えなくなる（9件）**

- COM3D2 H-Maps：既定の部屋のうち女の子の部屋・浴室・家のトイレ・ベッドルーム（行き先のシャワー・トイレを含む）。
- Project DIVA H-Map Collection：通信対戦の部屋。
- Honey Select 2 Map - Suite：場所「ホテルのスイート」。
- AnimationLoader と KPlug Animations：AL の体位の動き。
- Uncensor Selector とペニスの体（SoS Uncensor／BetterPenetration）：カードの「ペニスを見せる」（ふたなり）の描画と、対戦の挿入側の描き方。
- Studio BetterPenetration：挿入・口の奉仕での突き抜け防止。
- Strapons：ペニスの無い側の挿入で着けるもの。
- KK_Autostart と原作のキャラメイク：クリエイトを開くために。
- KoiSkinOverlayX（KSOX）と MaterialEditor：画像を使うカードの表示と、対戦での画像の照合。

**あると良い（2件）**

- ConfigurationManager：設定の窓を開くために（無くても設定ファイルの手直しで代替できます）。
- MoreAccessories：20個を超えるアクセサリを持つカードのため。
