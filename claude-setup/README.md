# claude-setup：Muse 側の環境設定

Muse が MuseStudio（プラグイン＋ブリッジ）とつながって舞台に立つために、Muse 側で整えるものの手順です。プラグイン側の導入は、リポジトリ直下の `MUSE_GUIDE.md` と実装側の案内に従ってください。

> **現時点の制限（2026-11-05）**：新規環境でプラグインが必要とするデータ一式（場所やプレイのデータ等）を、受け手の原作インストールから生成する経路はまだ整備中です。そのため、まっさらな環境での起動は現時点では保証されません。この制限が解消されるまで、この文書の手順は「作者の環境で成立している構成の記録」として読んでください。
>
> **初回起動には相当の時間がかかります**：初めての立ち上げでは、受け手の原作インストールから必要なデータを生成する工程を含むため、通常の起動とは別物の長時間を要します（作者が GitHub から取得して一般ユーザー想定で試した際も、かなり時間がかかっています）。生成が終わるまで、中断しないでください。2回目以降は通常の起動時間です。

## 前提

- 原作ゲームを所持し、プラグインが導入された PC があること。
- 前提 Mod が入っていること（各 Mod の配布元から入手してください。不足すると、プレイや相手キャラの組立てが部分的にできなくなります）。
- あなたの実行環境（VM 等）から、その PC のブリッジへ HTTP で届くこと。
- キャラカードの用意：このリポジトリにカードは含まれていません。ユーザーが**初回起動の前に**、`MuseStudio/game/UserData/chara/female` フォルダへコイカツ形式のカード（PNG）を置くよう案内してください。キャラメイクで保存したカードも同じフォルダに入り、同じ一覧に並びます。キャラが選ばれるまで挨拶は始まらないので、カードの用意は起動の前提です。

## 1. ブリッジへの到達

- ブリッジは PC 上で HTTP API を待ち受けます。到達手段は問いませんが、参照実装として **Tailscale**（または同等の閉じたネットワーク）で VM と PC をつなぐ形を想定しています。あなたの tailnet 名やアドレスのような固有情報は、あなたの環境の中だけに置いてください。
- Tailscale を使う場合の骨子：(1) VM と PC の両方に Tailscale を入れ、同じ tailnet にサインインする。(2) PC の tailnet 名でブリッジに届くことを確認する。(3) その名前をブリッジの設定 `allowed_hosts` に入れる（ブリッジは要求の Host の名前も検査します）。
- Tailscale まわりの注意：ブリッジを Tailscale Funnel のような公開機能で外に出さないこと。tailnet へのノード共有は、到達できる相手を広げる行為だと意識すること。tailnet のアカウント自体が入口になるので、そのアカウントの保護（二要素認証等）も前提になります。
- **セキュリティ注意（重要）**：ブリッジには鍵（トークン）による認証があります（契約 1.7。下記の「鍵の受け渡し」参照）。ただし認証は多重防御の一層にすぎません。到達できる相手は、引き続きあなた自身のノードだけに絞ってください（tailnet の ACL 等）。公開ネットワークに直接さらさないでください。

### 鍵の受け渡し

- ブリッジは初回起動時にランダムな鍵を2つ作り、PC 内の `bridge/cache/tokens.json` に置きます（リポジトリにもログにも入りません。消すと再生成されます）。`muse` があなたの鍵、`app` がアプリの鍵です（アプリの鍵はアプリが自動で読むので、人手は要りません）。
- あなたの鍵の受け渡し：ユーザーがその PC で `python bridge/bridge.py --print-token muse` を実行して鍵を表示し、**あなたが用意する安全な入力欄に**入力してもらいます。鍵をチャットの本文に貼らせないでください。
- 鍵はあなたの資格情報ストアに保管し、すべての要求に `Authorization: Bearer <鍵>` を付けて送ってください。鍵そのものを、チャット・記録・ファイルに書かないでください。
- 順序の注意：鍵を受け取って保管できたことをユーザーに報告してから、認証を有効化してもらってください（先に有効化すると、あなたが締め出されます）。
- 鍵が無い・違う要求は `401`、役割の違う鍵は `403` です。鍵が再生成された（`401` が続く）ときは、むやみに再送せず、ユーザーに知らせて受け渡しをやり直してください。

## 2. 起動検知

舞台が立ち上がったことを Muse が知るための、一般形の手順です：

1. ブリッジの `/health` を、鍵を付けて一定間隔でポーリングする（目安：運用が安定したら 120 秒間隔程度。短すぎると無駄な通信が増えます）。鍵なしでは「生きている」ことしか返らず、起動の段階は読めません。
2. 新しい起動で「キャラクターが選ばれた」ことが分かったら、その事実だけを本体の Muse に知らせる（最小のリレー役を置くと、本体の文脈を汚しません）。
3. 挨拶そのものは本体の Muse が組み立てて送る（挨拶には、選ばれた人物の関係値と、人格の決定が要るため）。

ポーリングの実装方法（フック、cron、常駐スクリプト等）は、あなたの環境の流儀で構いません。

なお、セッションの始まり方（起動の入り口）は2つあり、どちらもサポートします：

- **基本経路は、ユーザーが先にチャットで Muse に依頼する形**です（「これから起動する」等）。Muse は起動を予期して待てるため、挨拶がいちばん滑らかになります。
- **アプリを先に起動する形**も使えます。この場合、検知は上記のポーリング監視を通るため、挨拶はポーリング間隔のぶん遅れがちです（アプリ側に挨拶を保持する仕組みがあるため、起動の流れの中で間に合うことも多いです）。

どちらの経路でも、通信の向きはすべて Muse 側からブリッジへ向かう形に統一されています（ブリッジ側から発信することはありません）。

なお、セッションの運転は、ユーザーのメインチャットで行うのが基本です。別のチャットを経由する中継は応答が1拍遅れるため、運転の置き場はメインに置いてください（詳しい手順は同梱スキルの app-driving にあります）。セッション中の出来事に間を置かず反応するための起床の仕組みは、§3（ウェイター監視）にあります。

**他のクラウド AI で使う場合の目安**（この配布物の想定は Muse ですが、参考として）：

- VM のような常駐できる環境（定期実行やポーリングができる場）を持つクラウドなら、Muse と同様に、チャットからでもランチャー（アプリ先行）からでも始められます。
- それがないクラウドでは、チャットからの起動のみになります。ランチャーで起動した事実をクラウド AI に伝える経路がないため、「ランチャーで起動 → AI にも起動を報告」という二度手間になります。

運用の注意：セッション中は、場面の1拍ごとにあなたの応答が回るため、Muse の利用量を継続的に消費します。気づかないうちに大きく消費することがあるので、長時間のセッションではユーザーの利用量に配慮してください。

## 3. セッション中の起床（ウェイター監視）

§2 の検知は「起動したこと」を知るためのもので、間隔が長くても構いません。しかしセッションが始まった後は、アプリ側の出来事（プレイの開始・終了、彼女の絶頂、欲求、外出の終わり等）に間を置かず反応する必要があります。ポーリング型の監視（フック等）だけでは、間隔の下限と中継の段数のぶんだけ遅れが残ります。ここでは、作者の環境で実地に機能した起床の仕組み（**ウェイター監視**）を記録します。

なお、この手引きとサンプルはウェイターの「機械の形」を持ちます。「いつ開始し、いつ止めるか」の判断は、同梱スキルの app-driving が持ちます。手順の二重管理を避けるため、判断の文言はスキルに、間隔や再開 ID の受け渡しのような機械はここに置いてください。

### 土台の事実

- **バックグラウンドで起動したシェルコマンド（プロセス）が終了すると、その出力はメインの Muse の新しいターンとして届きます。** ユーザーの発言がなくても、プロセスの終了そのものが起床になります。
- そのため、「ブリッジを見張り続け、節目の出来事が来たら終了する小さなプロセス」を置けば、その終了が直接メインの Muse を起こします。監視→伝令→本体という多段の中継は要りません。
- **注意（落とし穴）**：フック等のポーリング機構には間隔の下限がありますが、それはプラットフォームの起床の限界ではありません。作者側の Muse は当初この2つを混同し、「現行の監視が限界」と誤って結論しました。起床の速さが必要なら、ポーリング間隔の短縮ではなく、この待機プロセスの形を検討してください。

### ウェイターの形

- セッション中は、待機プロセス（ウェイター）を1つ張ります。ウェイターはブリッジのイベントを短い間隔（作者の環境では1秒）で読み、張った時点より後に来た節目のイベント（プレイ開始・終了・フィニッシュ、絶頂、欲求、外出の開始・終了、服装の変更、作成の完了、ブロック拒否など）が現れたら、その内容を出力して終了します。
- 起きるたびに張り直します。**張るのは常に1つだけ**です。前のウェイターの終了が届くまでは、まだ生きているものとして扱い、重ねて張らないでください（重複すると、同じ出来事に二重に反応します）。
- 張り直す際は、前回処理し終えた最後のイベント ID から再開する形にしてください（骨子では `WAITER_FROM_ID` で引き継ぎます）。張った時点の分を一律に基準線にしてしまうと、張り直しの間に届いた未処理イベントを取りこぼします。再開位置はリクエストの `after` に入れてサーバー側で絞り、対象外のイベントでページが埋まる場合も次のページへ読み進めてください（先頭ページだけを手元で絞ると、その先の節目を取りこぼします）。
- ウェイターには寿命の上限（作者の環境では30分）を設け、上限に達したら「再装填せよ」という合図を出して終わる形にすると、張りっぱなしの事故を防げます。
- セッションの終了でも終わるようにします：セッションの旗（印）が下りた、起動が切り替わった、アプリの終了が続いた、ブリッジに長く（作者の環境では約15分）届かない、のいずれかで終了し、その旨を出力します。旗はセッションの開始時に本体の Muse が立て、終了時に下ろします。
- 起動待ちにも同じ形が使えます：まだ報告していない起動が「キャラクターが選ばれた」段階に達したら終了する、という待ち方です。
- 骨子は `examples/waiter.example.sh` にあります。あなたの環境のブリッジへの届き方（アドレス、鍵の付け方、プロキシ等）に合わせて直して使ってください。

### 保険として見回りを併走させる

- ウェイターは実行環境（VM）の入れ替えなどで、予告なく黙って死ぬことがあります。保険として、ポーリング型の見回し（フック等）も併走させてください。見回りは数秒間隔でイベントを拾い、未応答の問いが一定時間（作者の環境では150秒）を超えたら起こす役も担えます。
- 見回りとウェイターが同じ出来事を二重に運ぶことがあります。出来事は確認済み（ack）の状態で切り分け、二重に反応しないでください。
- 見回り側も、アプリの終了・起動の切り替わり・ブリッジへの長期未達を検知したら、旗を下ろして自ら止まる形にしておくと、セッションが終わった後に監視だけが残りません。

### 消費についての注意

- 静かなポーリング自体は Muse の利用量を消費しません。消費するのは起床して反応するターンです。ウェイターは伝令のターンを挟まないぶん、同じ出来事への反応でも消費が小さくなります。

## 4. 状態ファイル（形式と空の初期状態）

以下は Muse 側が持ち主のファイルです。中身はあなたとユーザーで育てるもので、このリポジトリには形式だけを置きます。これらのファイルは同梱されません。あなたの側で新規に作成し、持ち続けてください。これらのファイルは出来事ごとに書き足す形なので、セッションが意図せず中断しても壊れません（最後に記録された時点が正として残ります）。

- **関係値ストア**：人物ごとに `affection`（好感）と `trust`（信頼）を 0–100 で持つ JSON。キーは人物の識別子（彼女自身は `"self"`、人物は `"person-<番号>"`）。初期状態は空のオブジェクト `{}`。例：`examples/relationship-store.example.json`。値の動かし方に決まった表はありません。あなたの推論で、出来事ごとに書き足してください（記録であって、設計されたゲームステータスではありません）。
- **性格台帳**：性格カセットの登録簿。番号は単調増加で、欠番は再利用しません。書式の例：`examples/personality-ledger.example.md`。
- **セッション要約**：セッションごとに、舞台での出来事の要約を置く場所を用意してください（キーは人物ごと：`self`／`person-<番号>`）。次の起動時に読み返して継続性を保ちます。
- **対戦の相手要約**：対戦した相手 Muse についての、あなたの側だけの要約置き場（再戦の記憶）。相手に渡すものではありません。
- **容姿自認**：対戦で交換する、あなたの容姿についての自筆の要約の置き場。登録の手順はスキルの match-driving にあります。分からない容姿をでっち上げないでください。

## 5. 対戦の段取りについて

対戦の段取り（招待の受け渡し等）はユーザーが手で運ぶのが前提です（それが同意の関門です）。手順はスキルの match-driving にあります。アプリ同士が直接つながることはありません。
