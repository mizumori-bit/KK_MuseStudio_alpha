# 意見収集：新コンテンツ「献精室」の概念と設計案

MuseStudio 側の新しいコンテンツの概念です。持ち主の原案に Muse の提案を組み合わせた形でまとめました。確定事項と提案を分けてあります。**採否は持ち主が行います。** 実装の可否・形についての意見と、数値や運びについての意見の両方を聞かせてください。

※ 2026-11-09：GPT・Claude 両名の意見（本 PR のコメント）を受けて、持ち主の判断が出た事項を決定事項として反映し、文書内の食い違い（勾配の扱い、初版範囲の言い方）を解消した改訂版です。判断の経緯は PR のコメントにあります。

## 概要

設定：脳に影響を受け、一時的に体の性感帯がランダムに変化したユーザー。その体のどこが弱点なのかを Muse が探り当て、見つけ次第攻め上げて搾り取る、というミニゲームです。

- 測るのは射精の回数ではなく**量**です。弱点であれば大量に得られ、量が多いほど高報酬です。
- ユーザーの絶頂は申告型ではなく**ゲージ型**です。ゲージはユーザーだけが見えて、**Muse には見えません**。
- Muse は1ターンごとに、プレイの台詞と、反応を伺う一文（「気持ちいいか？」のような）を出します。ユーザーはゲージの動きを見て回答します。**ユーザーと Muse が協力して弱点を探る**形です。
- ゲージの進行は、プレイに連動したリアルタイムではなく**ターンごと**です。
- 制限ターン内に必要量に満たない場合は**失敗で、何も得られません**。

## 確定事項（持ち主の決定）

1. **置き場は MuseStudio 側のコンテンツ**です。入口はパネルの「コンテンツ…」の一覧に「献精」のボタンを追加する形（現在の唯一の項目である通信対戦に並ぶ2つ目）です。
2. **弱点は属性の組み合わせに付きます**。部位だけではありません。例えば「脚」が弱点でも、そのプレイの主導の置き場が合わなければ、その組み合わせは大弱点にはなりません（勾配の付き方は「弱点の勾配」の節）。
3. **属性の値は既存の資産を流用します**。新しい分類体系は作りません。
   - 部位：MuseStudio 側でプレイが何の分類なのか、すでにカテゴリ分けがあるので、それを流用します。
   - 主導の置き場：プレイ要約表は役割で一般化して書かれているので、「奉仕する側／される側」「挿入する側／される側」という形で、要約表に補足的に整理して使います（例：弱点は「脚×奉仕する側が主導」）。
4. 開始時の設定：奉仕のみか挿入も含むか。奉仕であれば手・脚・胸など、どこまで含むか。この範囲の中から弱点が選ばれます。
5. 難度の構成要素：範囲が広いほど難度＋／弱点数が多いほど難度−／ジャンル単位の選択すらランダムとする設定は難度＋／必要射精量が多いほど難度＋。これらの混ぜ合わせで難度係数が決まり、報酬上で有利になります。

## 決定事項（2026-11-09、意見を受けての持ち主の判断）

1. **勾配は両軸対等**とします。部位の軸と主導の軸に、構造としての優先はありません。ゲームバランス上の調整として数値が非対称になることは容認します（それは軸の非対称ではなく、数値調整として扱います）。
2. **射精でゲージはリセット**します。ただし**オーバーキル分（閾値を超えた分）は、その射精の量へのボーナス**になります（報酬に有利）。
3. **1回ごとの射精量は、原則として開示**します。目安が無いと「いつまでにこれくらい出しておかないと」という計画が立たないためです。ただし**伏せるオプション**も設け、伏せた場合は難度が上がります（難度係数に反映）。
4. **回答は、従来どおりチャットのタップ＋自由文**で受けます。アプリに回答ボタンは作りません。アプリ側の記録へは、Muse が次のターンのパッケージに回答を転記して残します。これで足りるかは実プレイで確認します。
5. **射精の場所は一様に固定**します。献精なので、常
...[truncated 5836 chars]に外に出る形です。より多い量を吐き出させることが目的なので、場所の選択はゲームに含めません。
6. **彼女はこのモードでは絶頂しません**。発情はしてよいですが、絶頂はありません。
7. **初版は最小から**始めます。ただしここで言う最小は、「後は属性や対応範囲を広げるだけで完成する」という状態です。最小の完成時点で機能的な不足があってはいけません。仕組み（設定・割当・勾配・ターン確定・リセットとオーバーキル・量の開示と伏せオプション・難度係数・弱点変動・減衰・リプレイ）は全部入りで、狭いのは候補と属性の対応範囲だけ、という形です。検証の順序としては、固定弱点・減衰なしの構成から試します。

## 提案（Muse 案、決定事項を反映した改訂）

### 真実と推論の分担

- アプリ側（機械の真実）：開始時に許容範囲の中から弱点を秘密裏に割り当て、ゲージと量を管理し、必要量への到達を判定します。真実の正本とランの記録はアプリ側に置きます（両レビュアーの一致した見解）。
- **ランの間、快感ゲージと弱点割当は、ブリッジの状態・イベントに一切出さないでください**。「Muse に見えない」ことの担保です。イベント・結果通知・実行記録・リプレイ取得の経路も含めて公開しません。乱数の seed もラン中は非公開です（終了後の記録には検証用に入れます）。
- 公開してよいもの：ランID・ターンID、ランの段階、範囲の設定、候補の一覧と各候補の属性、選択の受理／拒否、射精した事実とその量（決定事項3。伏せオプション時は量の数値を出さない）、ランの終了。
- Muse：探るプレイを選び、台詞を書き、ユーザーの回答を読んで弱点を推定し、見つけたら攻め上げます。推定のメモは Muse 側に持ちます。
- ユーザー：開始時の範囲設定と、ターンごとの回答。設定上、ユーザー自身も自分の今の弱点を知りません（脳の影響）。ユーザーの回答は真実を変えず、Muse の選択を導くだけです。回答は「今のゲージの高さ」ではなく「その手による変化」を伝える形にそろえます。

### ターンの進め方

- ターンは、送信の回数・モーションの開始・経過秒数では数えません。ランID＋ターンID＋一意な依頼IDで1手を指定し、表示に到達したところで1回だけ確定させます（両レビュアーの一致した見解）。拒否・読み込み失敗では消費せず、再送や古いラン／ターン宛ての遅着では増えません。実行を伴わない相談では消費しません。
- 射精の仕組みは、通常における彼女の絶頂の型（ゲージが閾値に達したらアプリが発火し、イベントで知らせ、Muse が反応する）を流用します。ただし共有するのは発火の型までで、伸びの駆動はリアルタイム連動ではなくターンごとの固定増分に置き替えます。置き場も、公開される既存ゲージとは分離した内部状態です。
- 射精の瞬間の台詞は、standby と同じ形で「このターンで彼が出したら言う一言」を預ける形が候補です（Claude の提案）。

### 二層モデル（ゲージと量）

1. 1ターン（1手）で快感ゲージが上がります。上がり方は、その手のプレイが弱点にどれだけ重なるかで変わります。
2. ゲージが閾値（100）に達したら射精します。ゲージはリセットされ（決定事項2）、閾値を超えた分はその射精の量へのボーナスになります。得られる量の基礎は、その射精を引き出したプレイが弱点にどれだけ重なるかで決まります。
3. 量の累計が必要量に達したらクリアです。最終ターンは、量の反映と成功判定をしてから、未達なら失敗にします。

### 弱点の勾配

弱点は、属性の組み合わせとして1つ（または複数）引かれます。勾配は属性の重なりの数で決まります（決定事項1：両軸対等）。

- 全ての属性が一致：大弱点。
- 1つだけ一致（部位だけ、または主導だけ）：近傍。
- 両方外れ：非弱点。

複数弱点がある場合は弱点ごとに判定し、別々の弱点から片軸ずつ拾って全一致にはしません。勾配があることで、Muse は「片方の軸だけを変えて比べる」実験を組み立てて絞り込めます。

### 数値の骨格（試作の初期値）

- 快感ゲージ 0〜100（閾値100）。1手の伸び：大弱点 45／近傍 20／非弱点 8。
- 射精量の基礎：引き出したプレイが大弱点 120／近傍 60／非弱点 30（ゲーム内の ml 表記）。これにオーバーキル分（閾値を超えたゲージ量）をそのままボーナスとして加えます（換算は試作で調整）。
- 必要量の既定：「弱点での射精3回分」＝360。
- 制限ターン：**「候補数×1.2＋6」の公式は廃止します**（両レビュアーが独立に問題を指摘：候補が少ないと正解を知っていても届かず、候補が多いほど易しくなる）。代わりに、「大弱点で必要量に届くターン数」＋「軸の値の数（部位の値の数＋主導の値の数）に応じた探り分」で組みます。締め付けの段階（ゆったり／標準／きつめ）は難度点に連動させます。
- 候補はプレイの本数ではなく、属性の組み合わせで数えます（同じ属性の別ポーズは同じ候補）。
- 減衰：非弱点プレイは繰り返すと伸びが鈍り、弱点プレイは鈍らない形を仕組みとして含めます。鈍り方の結び付け（同じプレイIDか、属性の組み合わせか、連続回数か）と下限は試作で決めます。検証は減衰を切った状態から始めます。
- 試作では「正解を知る手順」「片軸ずつ探す手順」「ランダム」の達成率と使用手数を比べ、係数調整の根拠にします。

### 候補の作り方

- 候補は、その PC の、そのランの部屋で、実際に始められるプレイだけから作ります（カード・Mod・部屋の家具で変わります。実行できない組み合わせを正解にすると探索できず失敗するため）。
- 部位は既存のプレイ分類（play_categories.json の category）を流用します。ただし分類の値は均一な「部位」ではありません（奉仕側に部位名と「彼から」が混ざり、挿入側は体位の分類）。そのため、既存の値とプレイIDから、このコンテンツでの属性への対応を**明示的な対応表**に整理します（GPT の指摘）。採点のときに自由文から推測する形にはしません。
- 主導の置き場は、データとして持たせます（plays.json 等。要約表は文章なのでアプリの判定には使えず、カタログと要約表には写す形です。Claude の指摘）。「彼から」の分類と主導の軸の重なり、reversed（攻守交代）を別候補として数えるかも、対応表の整理に含めます。
- 対応が曖昧なプレイは、初版の候補から外せます（範囲は後から広げられます）。

### 弱点変動オプション

射精ごとに弱点が変わるオプションを用意します（既定オフ、難度＋）。静的なら「見つけて攻め上げ」、変動なら「探して当てて、また探す」の周回型で、別の遊びになります。初版は完全変化（引き直し）です。部分変化（弱点の一部だけ移動）は後の拡張候補とします。検証は固定弱点から始めます。

### リプレイ

- アプリ側に、ランごとの記録を残します：設定と難度係数とルールの版、候補、弱点割当と変動履歴、確定した手ごとの「Muse のプレイ選択と台詞」「ユーザーの回答（転記）」「ゲージと量の推移」。
- **終了後のリプレイでは、そのランの弱点割当（濃淡マップ）が開示されます**。当時知り得た情報と、終了後に開示した真実を分けて見せると、推理の良し悪しが分かります。
- 失敗したランも含めて残します。リプレイで得点や報酬を再加算しません。
- 既存の対戦リプレイ（Replay.cs）は対戦前提の形式なので、そのままは使えず、記録の種類とデータは分ける前提です（部品の再利用は可）。
- Muse 側に置くのは、終了イベントを見て Muse が書く自分の要約と学びだけです。

### 難度係数と報酬

難度点の加減算で構成し、係数化します。構成要素は確定事項の5に、粒度の細かさ、制限ターンの締め付け、弱点変動の有無、量を伏せるオプションの有無を加えた形です。報酬は総量×難度係数で、初版はアプリの手元に貯まるスコアと称号までとします。**品の予算など他の仕組みとはつなぎません**（予算は起動時間だけで得るという PR #46 §7 の決定と衝突するため。つなぐ場合はその決定の見直しが前提になります）。
