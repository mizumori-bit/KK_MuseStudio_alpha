# パッケージ配送の信頼性（非対称性の解消）

外部の独立評価で挙がり、持ち主が対応すべきと判断した項目です。実装は Claude への引き継ぎとします。

## 現状（bridge.py のヘッダと実装で確認した事実）

- アプリ→Muse のイベントには、保存と ACK の仕組みがある（未 ACK のイベントは保持され、ack で初めて消える）。
- Muse→アプリのパッケージには、それに相当する仕組みがない。
  - パッケージは bridge のメモリ内 FIFO キューに保持される（上限 200 件 / 16MB、超過は 429）。
  - アプリは `GET /api/packages/next` で取り出すが、**取り出した時点でキューから消える**。アプリ側が受信したことを bridge に確認する経路はない。

## 失われ得る窓

- bridge の再起動で、キューに残っていた未表示のパッケージが消える。
- アプリが `/api/packages/next` で取得した直後、表示する前に落ちた場合、そのパッケージはどこにも残らない。
- 取得の応答が通信断で届かなかった場合も、bridge 側では取り出し済みとして扱われる。

`package_shown`（契約 1.15）は「表示された」という事後のイベントであり、Muse が表示の有無を後から知る手がかりにはなりますが、配送を保証する仕組みではありません。会話の連続性に直接関わるため、イベント側と同等の信頼性をパッケージ側にも持たせたい、というのが依頼の趣旨です。

## 依頼

配送の信頼性を上げる仕組みの設計と実装をお願いします。候補は例示で、設計は実装側の判断に委ねます。

- パッケージキューの永続化（bridge 再起動を跨いで残る）。
- パッケージへの受信確認（アプリが受信、または表示開始を確認するまで bridge が保持し、未確認分は再送できる形にする）。イベントの ack と対になる形が自然だと思います。
- 再接続時の未達分の扱い（新しい起動で旧パッケージを落とす現行の package_dropped の扱いとの整合も含めて）。

契約の形（エンドポイントやイベント）が変わる場合は、その旨を PR 本文に明記してください。スキル側の追随が要る変更であれば、Muse 側で対応します。
