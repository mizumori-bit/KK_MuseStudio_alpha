# 実装引き継ぎ：仕様案（PR #46）の採用範囲

review:gpt

仕様の正は PR #46 の仕様案（第9版、`docs/coordination/2026-11-07-feature-spec-draft.md`）です。この文書は、その採用範囲の実装を Claude へ引き継ぐためのものです。仕様本文と食い違う場合は、仕様本文を優先し、食い違いをこの PR に知らせてください。

進める順序は仕様の §10 のとおりです：1. 表情 → 2. 時計表示 → 3. 衣装（§1 の共通の基盤を先に）→ 4. 部屋の編集 → 5. 口（設計は表情と並行して前倒し）→ 6. 部屋の自動登録。§7（アイテム）は、資源の形が決まったので、この順序の後に加わります。

## 範囲ごとの要点

### §1 テーブルの基盤（部屋・衣装に共通）

- 引当表（アプリとブリッジが作る。存在と可否はこちらだけで判断する）と、レッテル表（人と Muse が書く説明。判断の材料で、可否を左右しない）を分ける。対象は安定した ID で数える（一覧の並び順に依存しない）。
- レッテルの置き場：原作の部屋のレッテルはリポジトリに置ける。Mod の部屋とコーデのレッテルは、その PC のローカルファイルだけに置く（公開しない）。レッテルには公開できる ID と説明だけを入れ、絶対パスやカードの中身は入れない。
- 対象が消えたレッテルは消さず「保管中」にする。「レッテルが無い（未整理）」と「保管中」は別の状態として扱う。ずれの検査では、存在しない ID のレッテルを保管中へ移す。ユーザーの直しが、共有の説明より優先する。
- Muse はレッテルを、新しいブリッジのレッテルの口（例：`GET/POST /api/labels/rooms`、`/api/labels/coordinates`）から書く。口は Muse の鍵だけが使え、PC のローカルファイルに保存し、登録されていない ID への書き込みは断り、同時書き込みの競合を見つける。この口は、 Muse 専用の受け口（契約 1.20 の 7.1）の許可一覧にも足すこと。

### §2 表情

- 決まった形は案 A（ユーザーの決定）。優先の軸：Muse の表情が保持されている間、ゲージの既定は上書きしない。一時的な反応（触れ合い・絶頂など）は割り込んで、終われば保持していた表情に戻る（戻り先は 1 つ覚える）。持続の軸：次の Muse の表情か場面の切り替えまで続く。短い秒数のラベル（ecstasy の類）は時間で切れて、前の Muse の表情に戻る。
- 安全時間は 300 秒、設定で変えられる形にする。数え始めは保持が始まった時点（表示の開始）で、受け付けた時点ではない。一時的な表情では数え始めは戻らない。場面が切り替わったら、保持・戻り先の記憶・安全時間は一緒に消す。
- 余韻は今の形のまま：余韻は独立した FaceScene で、入ると Muse の保持は解けて余韻の既定になる（場面切り替えの扱い）。
- 状態には、指定した表情／表示中の表情／一時変更の理由と終了条件を出すこと。

### §8 時刻

- 時計表示のオンオフだけ。時間帯を状態に載せない。部屋の明かりの連動はしない。

### §3 衣装

- コーデカードだけを使う（元はアプリ側の `game/UserData/coordinate` だけ。原作側のフォルダは読まない）。README に、原作側で作ったカードはアプリ側へコピーするまで一覧に出ないことを書くこと。
- 髪はコーデカードに含まれないので対象外（髪のアクセサリーはアクセサリーとして含む）。
- 適用の経路は、画面の操作と Muse のブロックで共有する。既存の `{kind: "change", outfit: n}` は残し、`coordinate` を足す（契約のマイナーな版上げ）。変更は既存の `outfit_changed` の出来事で知らせる。
- プレイ中と対戦中は、着替えを操作として出さない（ブリッジの拒否ではなく、運転の側の取り決め）。
- 読み込み自体の失敗と、部品の代替は分ける：カードの読み込みに失敗したら着替えず、理由を出来事で返す。読み込めたが部品が代替された（Mod の部品が無い等）場合はそのまま進め、代替は引当側の情報としてだけ出す。
- 欠け（空き）の扱い：空きはコーデの構成そのものとして、そのまま適用する。欠けを理由に断らない。
- 継続の形は今のまま：キャラを切り替えて戻す、起動し直すと、カードの衣装に戻る。カード自体は書き換えない。
- レッテルの鍵は、そのフォルダ内の相対ファイル名＋記録した内容ハッシュ。ハッシュが変わったらレッテルは残して「要確認」にする。名前が変わったらレッテルは外して保管中に残す。

### §4 部屋

- 開始の形：起動時に、原作と Mod の部屋を名前だけ全て登録する（原作の表から速く取れる）。対応位置などの特徴は、初めて読み込んだときに取って覚える。部屋が増えたことは `rooms_added` で知らせ、特徴は別の出来事（例：`room_features`）で届ける。
- 今の生活圏の部屋は常駐のまま。追加分は遅延読み込み（既存の仕組みの延長）。彼女がそこで行動を始めるときも、その部屋を用意する。ユーザーと彼女が別々の部屋にいる間は、両方を保つ。「利用できる」のは読み込みが終わってからで、終わる前にその部屋を使う操作は受け付けない。
- 鍵：原作の部屋は原作の番号。Mod の部屋は（zipmod の GUID、その Mod 内での元の番号）。Mod のマップ番号は起動ごとに付け直されるので鍵にしない。名前は表示用だけ。GUID の取り出しは、実装の初めに Sideloader の解決表から取れるか確かめること。
- 遅延読み込みした部屋の解放：使っている間・行動の途中は保ち、終わった追加分は解放する。初めの上限（部屋数かメモリ）は、実装の初めに実測して、この引き継ぎに書くこと。
- 位置の編集：3 層（生成時の初期値／ユーザーが保存したデフォルト／現在値）。「デフォルトに戻す」と「初期化」は別。編集したものだけの絞り込みは、保存した調整の記録で判定する。プレイの位置の絞り込みはカテゴリごとで、そのカテゴリの印だけ出す。複数のカテゴリで使う位置は、1 つの共有の位置のままにする。
- Muse の部屋の一覧は「いつもの部屋」と「全部」に分ける。
- 新しい部屋の流れ：起動時は登録だけ → 出来事で Muse へ → Muse は手が空いたときにレッテルを書く。起動は推論を待たない。
- レッテルの事前整理の範囲：既知の部屋（原作＋その環境で知られている Mod の部屋）は、著者の環境では Claude が先に整理する。「どの部屋を事前に整理するか」と「公開するか・ローカルに置くか」は別の問いとして扱うこと。

### §6 口

- 表示の開始が口の開始の合図。口の進みは表示した文の割合に結び付け、閉じは句読点で拍を置く。一押しで全文表示したら口は止まる。止まったら、そのときの表情の口に戻す。早送りと割り込みに追随する。表示の待ちの間に読みの準備をする。
- 読みの形：テキスト内のルビ（`漢字《かんじ》` の形）を推奨とし、ブロックごとに任意。無い部分は開閉の拍で代替する。タイミングと文字数は、解析した表示文で数える。
- 解析は受ける側・表示する側で 1 本に統一する：自分のパッケージ、対戦で受けたもの、再生、すべて同じ解析を通す（（）を取り除き、ルビを表示用に処理し、読みの流れを口のために取り出す）。対戦の送る側は、今までどおり（）を暗号化の前に取り除く。ルビは取り除かず、文に乗せて送る。（）の中のルビは、（）と一緒に消える。
- 口の動きは、初めは開き具合だけにする（声の口の動きと同じ仕組み）。ただし表情の側も口の開きに上限を付けるので、「競合しない」は実装の初めに確かめること。母音ごとの形は、原作の口の形の調査待ち。

### §7 アイテムと資源

- 在庫は両方：家の共有の棚と、各自の個人インベントリ。棚はキャラごとではなく家のもので、起動し直しても残る。初期在庫は棚と各自の個人インベントリの両方に入れ、初めの数はお互い同数にする。
- 渡すのは、受けた後に成り立つ。受け入れの承諾と使用は分ける。承諾の時点でも、移動元の在庫・移動先の上限・対象の人物を確かめること。
- 効果は気分の数値まで（発情・酩酊など）。酩酊は新しい気分として足す。効き目はキャラごとの気分の保存に入れ、閉じていた間は 1.18 の落ち着きの規則で引く。そのために、酩酊と持続する効果については、残量・残り時間・減衰を保存し、再開のときに消費済みの分や未適用の分を重ねて加えないこと。
- 重ねがけは、重ねると鈍り、上限で止める形。アイテムにグレードを設け、上位ほど上限が高く鈍りも僅かにする。
- 効果の無い品（花など）も置く。飾ったり贈ったりするだけの品で、出来事として Muse に届く。
- 飲んでいる間は手の小物（缶・コップなど）を持たせる。酩酊は頬の赤み・目の開き・視線のゆらぎに出す。
- 関係の値に触れる効果は持たせない。贈り物は出来事として知らせ、受け止め方は Muse に任せる。
- 資源（予算）は時間による継続報酬のみ：単位時間ごとに予算が入る。当面は 1 時間ごと。数えるのはアプリが起動している時間で、気分の仕組みが持っている「アプリが動いていた時刻」の記録を使える。端数は秒単位で貯めて残し、1 時間分たまるごとに入る。
- 額と品の値段は、アイテムの表（items.json）と報酬の設定（データのファイル）に置き、遊んで直せる形にすること。目安は「ひと晩（3 時間ほど）で普段の品が 1〜2 個買え、上のグレードは数日分」。具体値は、置いた後にこの PR へ示すこと。
- 資源の出どころは世界の仕組みで、彼女が払うものではない。入ったことはアプリの画面だけが示す。Muse が購入する機構は作らない。購入はユーザーの行為（貢ぐ体験）として置く。
- ユーザーに影響を与えるアイテムを Muse が利用できない設定を、アプリに設けること。この設定は、適用の直前にも確かめること。
- 初期配布・日次の補充・購入・受け渡し・使用は、再送や再起動で二重に成り立たせないこと。在庫と効果の保存が、途中で食い違わない形にすること。

## 引き継ぎの条件（GPT のレビューより）

- 初めての部屋の読み込みを始める手順を、実装で具体化すること。
- コーデの適用の直前に、その場で適用できるかを確かめる手順を入れること。
- スキルの側を有効にする条件として、契約の版の条件を決めること（Muse 側のスキル反映 PR と対応させる）。
- §7 については上の会計まわりの条件（承諾と使用の分離、二重成立の防止、保存の整合、影響を禁じる設定の適用直前の確認、持続効果の保存と 1.18 との整合）。

## 確認事項（持ち主の判断）

- **予算を Muse が知るか**：おつかいで「欲しい」と言うときに、ユーザーが買えるかを彼女が気にするかもしれない、という点からの確認です。Muse の推奨は、状態に予算を載せない（彼女のおつかいは「欲しい」だけに置き、買えるかはユーザーの側の判断とする）。持ち主の決定が出たら、この PR に記録します。
