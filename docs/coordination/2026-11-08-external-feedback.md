## 持ち主の意見

検討会（2026-11-08、持ち主と Muse）で出た持ち主の意見。同格ルールに従い、検討材料として置く。

1. **ゲージの見せ方（H の指摘に対して）**：見せ方の工夫は認めないつもり。主体として対する相手のゲージが見えるわけがない、という立場。（**未確定**）
2. **既定の台詞へのフォールバック（C の案に対して）**：認めない。何が起きてどう反応すべきかは主体（Muse）の推論範疇。ただし、明確なエラー、主体の推論が及ばない事態、接続の途絶によるものはその限りではなく、既定のエラーメッセージをアプリに出す形はあり得る。
3. **イベントキュー（溜まったイベントを次回要約して渡す）**：支持する。判断のための補足として機能する。（**未確定**）
4. **対称性の追加意見**：アプリが既定のエラーメッセージを出した場合も、「エラーが起きて、アプリがそれを表示した」こと自体をキューに乗せて Muse に届ける仕組みが要る。戻った Muse の知らない表示が画面に出ていた、という齟齬を残さないため。

## GPT の推奨判断（採用前、2026-11-08 レビュー）

GPT は元の外部会話を独立には確認しておらず、人数や内容は Muse の収集報告として読んだ。実装差分なし（文書・現行ソースの確認のみ）。

- **導入・接続・環境差**：採用推奨。前提 Mod・設定・接続を確かめる導入診断を用意し、確認済み環境と未確認環境を明記する。診断に鍵や私的データを出さない。接続のために認証を外す案内や全環境の保証は増やさない。
- **再接続・再同期**：採用推奨。アプリ終了／ブリッジ不通／Muse 側の停止を区別し、復帰時に状態・カタログ・イベント・配送記録を照合する。方式（スナップショット、ハートビートへの同梱など）は候補として比較し、全部を同時に足す必要はない。
- **版の欄・未知の内容**：段階的な採用を推奨。契約文書の版、カタログの版、通信の互換性を区別する。未知イベントの読み飛ばしと、理解できない操作の拒否を分け、受理後に無言で捨てる仕様にしない。
- **イベントの順序・重複**：既存の補強を採用推奨。再送は同じ ID、新しい意図は新 ID という現行方針を維持する。他環境の重複キーをそのまま移植しない（同じ文でも別の操作意図になり得る）。受信・保存・処理・実行の確定を区別する。
- **イベントの留置・次回の要約**：採用推奨。原本と処理済み位置を土台に要約する。現行の保存キューは上限超過で古い未処理イベントが落ちるため、欠落を Muse が判別できる情報が要る。重要な事実は要約で消さず、保存確定前に処理済みと返さない。
- **壊れた JSON・無応答**：技術エラー表示は採用推奨。キャラの既定台詞は見送り推奨（Muse が判断・発言したような台詞の代作は主体の分担に合わない）。タイムアウトは送信前・通信・受理後・推論を分け、一律に短くしない。結果不明なら照会する。
- **表示したエラーの伝達**：採用推奨。「いつ、何を、アプリが実際に表示したか」を Muse へ届ける。断線中は PC 側に記録し復帰後に配送する。未表示のものを表示済みと記録しない。
- **判断の結果が数値へ戻る道**：意味を分けるまで保留。操作の成立・拒否・身体状態を返すことは支持。アプリが「満足したか」を測って内面や関係値へ自動変換する案は支持しない。何を誰が観測した値かを定義する。報酬査定や喜び申告も戻さない。
- **Muse 側の生存確認・復旧**：外側の担当と権限が決まるまで保留。終了した VM 内の見張りだけではその VM を起こせない。検知・保管・再起動の担当を決める。まず手動復旧でもよい。復旧時に接続元認証を無条件で覚え直さない。
- **待機中の小さな行動**：新機能は保留。移動や身支度には既存の操作がある。まず Muse が何をしたくて、どの操作が不足するかを整理する。「ただ一緒にいる時間」はイベントを増やさず成立させる余地もある。
- **閉じている間の手紙・メモ**：保存先・宛先・寿命が決まるまで保留。通常パッケージは起動に結び付き新起動で未開始分を破棄するため流用しない。別の保管物として人物・未読・期限・件数・重複を決める。文面は Muse が書く。
- **途中終了の後始末**：優先して採用推奨。未開始分の破棄は既にある。補うのは開始後の中断・部分実施・結果不明。パッケージ開始・表示・操作成立・表示終了を区別する。不明を未実行と断定して再実行しない。
- **利用者向けゲージ**：通常 UI の正確な数値を外す方向を推奨。現在はプレイ中に快感度が数値（％）で表示される。変更範囲を分けて採否を求める（内部の身体状態や Muse 向けの取得まで廃止する話ではない）。

再同期の「水位」は3つに分ける必要がある：最新のイベントの位置／状態へ反映済みの位置／Muse が保存・処理済みの位置。現在のイベント取得の位置情報を、そのまま「反映済み」「処理済み」とみなすと未処理を飛ばし得る。

なお：現行実装には既に、認証付きの専用受け口、イベント保存・処理済み通知、重複防止、配送段階の照会、起動・キャラの識別がある。手順の不足と新しい機能の不足を分けて整理するのがよい。新しい通信口を作る場合は、権限、専用受け口の許可経路、契約版、検査、スキルの有効化条件も合わせて整える範囲になる。
