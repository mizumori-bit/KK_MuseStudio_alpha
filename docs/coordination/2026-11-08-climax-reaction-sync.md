# 意見募集：アプリ側の絶頂通知と Muse の反応の「ずれ」を一致させたい

`review:gpt`

## 問題

アプリは絶頂を即座に提示する（ゲージ・演出）が、Muse の反応台詞は構造的に後れる。2026-11-08 夜の実セッション（契約 1.38）で、持ち主の所感として「想像以上にずれが大きい」との指摘がありました。

2026-11-08 の GPT 回答を受けて、Muse が論点と数字を整理し直した版です。次に Claude の実装側の見解を集め、最後に持ち主が採用範囲を判断します。採用判断までは実装を開始しないでください。

## 数字の整理（GPT の訂正を受けたもの）

- 実例：23:33:31 の彼女の絶頂（masturbation_01、pace 3）に対し、反応パッケージの送信は 23:34:10。**この約39秒は「発生から送信まで」であり、送信後の表示キュー待ちを含みません。** この実例だけで遅れの主因を表示待ちへ割り当てることはできません。また「起床約1秒」「推論 数秒〜十数秒」という概算と39秒との差は未分解です（別ターンの処理待ち等が含まれ得ます）。
- もう一つの実例：23:18:33 の彼女の絶頂（sonyu_18、pace 3）。反応は後続ターンとして送信。
- 計測の宿題（Muse／Claude 共同）：発生／イベント取得／Muse の処理開始／送信／ブリッジ受付／最初の表示を、同じイベントとパッケージで対応付ける。既存の package_shown には received_ms・shown_ms・waited_ms があり、受付から最初の表示までは切り分けられる。反応がパッケージ途中にあると最初の表示時刻とずれるため、計測用の反応は先頭に置くか、対象ブロックの時刻を別に記録する。別PCとの時計比較では時計差も確認する。

## 案と GPT の評価

### 案A：アプリ側が絶頂提示を Muse の反応まで保持・延長する — 見送り推奨

- 発生・カウント・顔・動作を返答待ちにすると、数値と体の出来事、通知、見た目の時点が分かれる。約40秒の不足を余韻の延長だけで埋めると、その間の停止・体位変更・次の出来事にも影響する。
- 余韻の見せ方を短く調整する余地は補助案として残るが、遅れてきた反応との完全同期を保証する手段にはしない。

### 案B：マイルストーンでの事前通知 — 採用候補（条件付き）

- 0.85 の予告（設定 near=0.85 と gauge_milestone）は**既に実装済み**であり、同種イベントの追加は不要。Muse 側では、公開ウェイター骨子の節目一覧に gauge_milestone がないため、near を起床対象に加える変更は検討できる。
- ただし、同じ加算で near と climax が続けて通知されることもあり、0.85 は一定秒数の猶予ではない。プレイ開始時や直前の通常ターンでの準備も使える形がよい。
- **「事前に用意すること」と「発生まで表示を待つこと」は別の機能として設計する。** 現行の通常キューへ事前反応を送るだけでは、発生前に台詞が出る場合がある。

### 案C：反応の優先表示 — 限定して採用候補

- 表示待ちは減らせるが、推論にかかる時間は減らない。これだけでは39秒級の遅れは解消しない。
- 汎用の優先度付きキューへ広げず、短い反応の表示に限定する。現在の台詞の区切りで入れるか、途中で打ち切るかを決める（区切り待ちは、その分
の遅れが残る）。
- 条件：割り込んだ後の古い台詞・選択肢・操作を再開するか破棄するか。既に実行した操作は戻さない。中断・破棄・表示済みの記録をどう残すか。

### 案D：条件付き反応（Muse が事前に用意し、アプリが発生時に表示）— 本命の採用候補

- 発火判定はアプリ側、文面と表現の選択は Muse 側。Muse があらかじめ「この出来事が起きたら、この短い反応を出してよい」と用意し、アプリが実際の発生に合わせて一度だけ表示する。推論を発生後に必ず挟む構造から離れられ、文面の主体も Muse のまま保てる。アプリが台詞を勝手に生成する形にはしない。
- 実装前に必要な条件（GPT）：
  - 待機する反応は通常 FIFO と分け、受理・保存と、発火・表示を区別する。
  - 起動・キャラ・プレイの番号・対象の体／発生回を結び付ける。終了・変更・キャラ切替・再起動・期限切れで失効し、二重表示や次の場面への持越しを防ぐ。
  - 発火時の状態にも合うものだけ出す。最初は台詞と対応する表情などの表示に絞り、着替え・移動・アイテム使用等の一般操作まで条件付きにしない。
  - 準備が無い／古い場合も、実際の発生・数値・演出は待たせない。後から届いた文章は、既に起きた出来事への反応として扱い、同じ出来事をもう一度起こさない。
  - 主対象は通常セッションのゲージ由来の発生。対戦の declare や通常会話の anim は既に別の発火規則があるので、一括で混ぜない。
- これは新しい契約機能である。現行の未知欄は実行されないため、スキル側の書き方だけでは実現しない。採用後に、契約の版、待機・発火・失効の記録と配送上の扱いを定義する必要がある。

## 「一致」の目標（GPT 提案）

- 発生・カウント・既存の身体側の顔と動作は、その時点で進む（待たせない）。
- 有効な反応が事前に準備され、画面遷移や別の発話との競合がない場合は、発生→反応表示開始を1秒以内にすることを暫定の設計目標とする（現時点の実測値や保証ではない）。
- 競合時は、台詞の区切りを尊重するか即時に割り込むかを先に決め、その条件で遅れを測る。
- 事前準備が無い状態で発生後に作る自由な長文の完全同時表示は目標にしない。短い反応を合わせ、詳しい反応は後のターンに分ける。
