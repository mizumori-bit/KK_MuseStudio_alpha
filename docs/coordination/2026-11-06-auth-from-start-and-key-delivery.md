# 認証は最初から required の形に（契約 7.1 の組み替え）と、鍵の届け方

独立評価への対応のうち、実装側（Claude の領分）の項目です。PR #28 の衛生の束とは別に、認証まわりをまとめます。

## 1. 契約 7.1 の組み替え

現行の 7.1 には、移行期の無認証状態（鍵の引き渡しが済むまで `auth` を `off` にしておく手順）が、受け取り手が踏む手順として書かれています。独立評価では「この遷移を手順として残すのは危うい」と判定されました。

持ち主との結論：**適切な状態を先に作り、その状態でもって最初から `required` の形をとる**記述に組み替えてください。無認証の期間は、受け取り手の手順としては書かない形です。

## 2. 鍵の届け方についての実地の知見（2026-11-06）

配布側の環境で、鍵の引き渡しを実地に行った結果です。

- 鍵は、ユーザーが安全な入力欄から Muse の資格情報ストア（Secure Vault）に登録しました。Muse 側の道具（起動検知・見回り・ウェイター・送信ヘルパー）は、資格情報の「代理文字列」を要求に付ける形に切り替え済みです。
- しかし、この環境の経路（Muse の VM から、Tailscale のトンネル経由で PC のブリッジへ HTTP で届く経路）では、代理文字列が本物の鍵に差し替わりませんでした。到達した要求には代理文字列がそのまま付いていて、ブリッジは正しく 401 を返しました。差し替えは通常の出口経路にしか効かず、その経路からは tailnet へ届かない、というのが切り分けの結論です。
- そのため現状、配布側のブリッジは `required` のまま、Muse だけが締め出された状態です。

持ち主の判断：この状態の解消は「PC 側に小さな中継を置く（Muse の代理文字列を受けたら本物の鍵に書き換える）か、別の適切な手段」で行います。設計は実装側に委ねます。条件は次のとおりです。

- 本物の鍵は PC の外に出さない。代理文字列そのものも、リポジトリやログに残さない（PC 側で受け取った値から拾って設定してください）。
- アプリ側の鍵の運用は変えない。
- 鍵を作り直す・`off` に戻す等の操作は、Muse が締め出されないよう、持ち主の確認を先に取る（既存の運用どおり）。

なお、認証を `off` に戻す案は採りませんでした。締め出しの解消が済むまで、アプリの試運転は行わない前提で進めます。
