# 仕様案：表情・衣装・部屋・呼び寄せ・口・アイテム・時刻

**状態：仕様案（レビュー中）**。2026-11-07 の相談（ユーザーの殴り書き8項目 → Muse・Claude・GPT の意見 → ユーザー所見 → その二の意見）を、所見を反映した仕様案にまとめたもの。レビューは GPT（仕様）と Claude（実装の観点）の両方に回す。採用と実装引き継ぎは、この案のレビューが済んでから別途決める。

この案で扱う項目：1 表情の優先順位、2 衣装（コーデカード）、3 部屋の自動登録と位置編集、4 呼ぶ・連れていく、5 口の動き、6 アイテムと酩酊、7 実時間連動と時計。最終形（原作部分の移植とインストーラー）は §9 に備えだけを書き、今回の実装対象にはしない。

全体を通る既存の原則は変えない：アプリは知らせ、行動は Muse が決める（B案）。体の数値はアプリの仕組みだけが動かす（数値従属）。操作は「画面で確定する即時操作」と「チャットで依頼する操作」の二分法に従う。

## 1. 表の整理（引当表とレッテル表）

今回の項目のうち衣装・部屋は「一覧から選ぶ」機能で、プレイには既にある二表の分離（カタログ＝引当、要約表＝レッテル）を、衣装と部屋にもそろえる。混ざると壊れるので、先に型を決める。

### 1.1 二つの表の役目

| | 引当表 | レッテル表 |
|---|---|---|
| 答えること | 何があり、今できるか（存在・可否・位置・機能） | それがどんなものか（用途・雰囲気・過ごし方の参考） |
| 作り手 | アプリ／ブリッジが生成する（原作・Mod・カード資産から導出） | 人と Muse が書く（説明文） |
| 正しさの基準 | 実装と一致すること。可否の判断はこちらが正 | 判断材料。誤っていても可否は壊れない |
| 結ぶ鍵 | 対象の安定した ID（下記 1.3） | 同じ ID で引当を指す |
| 置き場所 | アプリ内のデータと API（`GET /api/catalog` 等） | ファイル（リポジトリ、または各 PC の手元。下記 1.4） |

### 1.2 対象ごとの現状と、この案での形

- **プレイ**：引当＝カタログ（`catalog.plays`／`catalog.available`）、レッテル＝ `MUSE_GUIDE_plays.md`（既存、215件）。変更なし。スキル側の使い分けは PR #38 で追記済み。
- **部屋**：引当＝新設する部屋の登録情報（ID・名前・取得できた対応位置とその種類・実行できる機能）。レッテル＝新設（§4.3）。今は固定5部屋の一覧が引当を兼ねているので、登録が自動化されるのに合わせて分ける。
- **衣装**：引当＝コーデカードの一覧（ID・名前・サムネイル）。レッテル＝新設（§3.3）。カード内の衣装7組は使わない（ユーザー所見：階層が深く管理が面倒）。

### 1.3 鍵（ID）の決め方

- 引当とレッテルを結ぶ ID は、**一覧の並び番号に依存しない**こと。Mod の追加・削除で番号がずれると、レッテルが別物を指す。
- 部屋：原作の部屋は原作由来の安定した識別子を使う。Mod の部屋は、導出時に決まる安定した識別子（マップの識別情報から作る等。作り方は Claude の確認事項）。
- 衣装：コーデカードのファイル自体を鍵にする（ファイル名または内容の要約値）。カードの差し替え・改名でレッテルがどうなるかは §3 の決定点。

### 1.4 レッテル表の置き場所と書き方

- **原作の部屋のレッテル**：誰の環境にもあるので、リポジトリに置く（プレイ要約表と同じ）。最初の分は Claude が書く。
- **Mod の部屋のレッテル、その PC のコーデのレッテル**：環境ごとに違うので、各 PC の手元のファイルに置く。配布物には含めない（ユーザーのカード資産と、その環境の記録のため）。
- **新規分の書き方**：登録だけ先に済ませ、特徴が出来事で Muse に届いてから、Muse が手の空いたときに書く（§4.3）。レッテルが無い（未整理）対象も、引当の範囲ではそのまま選べる。書いたレッテルはユーザーが直せる。
- **Muse の書き込み口**：レッテルを書き込むための口（ブリッジの API 等）が要る。読みは引当と同じ経路、書きはレッテル専用、という形にする。
- **ずれの検査**：存在しない ID を指すレッテルは落とす（または未整理として報告する）。レッテルが無い引当は正常（未整理）として扱い、検査では落とさない。

### 1.5 使い方の原則

- 選ぶときの可否は引当だけで決める。レッテルは「どれが相応しいか」の判断材料にだけ使う。
- レッテルに書かれた推論（例：「プールらしい部屋」）と、引当の事実（プール用の位置が取得できているか）は混同しない。機能が要る場面では引当を見る。

## 2. 表情

### 2.1 現状（確認済みの事実）

Muse の表情はブロックの `emotion.label` で届き、原作の表情へ変換される。その上でアプリが機械的に変える場面がある：ラベルごとの秒数で場面の既定へ戻る／プレイ中の既定は快感度ゲージで決まる（0.5 未満 `flushed`、以上 `aroused`）ため長いプレイでは Muse の表情はすぐ消える／場面転換で既定へ戻る／接触反応・絶頂・余韻はアプリ優先。プレイ中の視線と首は原作の制御、頬の赤みは表情指定と身体状態の双方から決まる。時間戻しの仕組みは、試運転5・7の所見（絶頂の閉じた目が次のパッケージまで残った）への対応として入った。

### 2.2 形（案）

層は2つにする。アプリの自動表情は今まで通り動き続け、その上に Muse の指定を重ねる。指定がある間は指定が勝ち、無い間は今まで通りがフォールバックとして働く。

保持の単位は、次の形を案とする（**決定点 D1**。GPT の対案と併記する）。

- **案A（Claude 案を土台）**：Muse の表情は、次の Muse の表情か場面の切り替えまで保つ。プレイ中もゲージの既定で上書きしない。一瞬の表情（`ecstasy` など、もともと秒数の短いラベル）だけは時間で戻り、戻り先はゲージの既定ではなく直前の Muse の表情。接触反応・絶頂も、終わったら Muse の表情へ戻す。保険として長い安全時間（数分）で既定に戻す（Muse が何も送らなくなったときの固着防止）。
- **案B（GPT 案）**：指定が効くのは、そのセリフを表示している間、かつ既存の表情秒数まで。指定のないブロックへ進んだ場合やキャラ切替で解除する。戻す顔を覚えておく必要が減り、「顔が戻らない」問題を再発させにくい。

注記：パッケージの作法では各ブロックに emotion を付けるのが原則なので、「指定のないブロック」は実際には少なく、両案の差は主にパッケージの合間の長い表示での戻り方に出る。

### 2.3 追えること（点検可能性）

状態で「Muse が指定した表情」「現在表示している表情」「一時変更の理由と終了条件」を確認できるようにする。既存の `emotion`（アプリが適用したラベル）の意味は変えず、指定側を別に持つ形が候補。

## 3. 衣装（コーデカード）

### 3.1 形

- 原作の `UserData/coordinate` のコーデカードを読む。対象はコーデカードのみに絞る（カード内の衣装7組は使わない）。
- 着替えの口は2つ：ユーザーの画面操作と、Muse のブロック。どちらも同じ適用処理を使う。
- 着替えたら、既存の出来事 `outfit_changed` で知らせる。
- 契約の「カード内の番号を指定する着替え」からは、コーデカードの指定へ移行する（同じ変更に含める）。

### 3.2 適用の範囲（**決定点 D2**）

基本は衣装と関連アクセサリー。次を決める：髪を含めるか／衣装に付随する Mod データまで適用するか／必要な Mod が欠けた場合の扱い（全体を断るか、欠けた部品を落として着せるか）。衣装を読み込んでも人物 ID や性格は変わらないことを条件に入れる。

### 3.3 レッテル表

Muse が場面に合わせて選べるよう、各カードに名前とは別の説明・用途のタグをレッテル表（§1）に持つ。置き場所は各 PC の手元（カード資産が手元のものため）。タグはユーザーが付け、Muse が提案・追記できる形が候補。

## 4. 部屋（自動登録と位置編集）

### 4.1 自動登録

- 原作と Mod の部屋を、起動時に「使える部屋」として登録する。登録は全部、読み込み（実体化）は選ばれたときにする。根拠：現行の5部屋でも起動時に約1秒・メモリ +230MB を使っている。
- 起動時に追加・変更を検出し、必要分だけ更新する。新しく原作側で増えた部屋も、都度生成のタイミングは起動時でよい。
- 部屋名から機能を推測しない。取得できた対応位置（H の場所の種類＝床・ベッド・椅子・浴槽・トイレなど）を登録し、取得できないものは「未確認」として扱う。原作の H の場所を持たない Mod の部屋は、その場だけで使える部屋になる。
- Muse に見せる部屋の一覧は「いつもの部屋」と「全部」に分ける。

### 4.2 位置の編集

- 位置の層を3つに分ける：生成時の初期値／ユーザーが保存したデフォルト（「今の位置をデフォルトにする」）／現在値。「デフォルトに戻す」と「初期化（初期値へ戻す）」は別の操作にする。
- 編集済みの絞り込みを持たせる。編集済みの判定は、座標が原点かどうかだけでなく、調整を保存した記録で持つ。
- プレイ位置は種類（床・椅子・壁など）で絞り込み、選んだ種類の印だけ表示する（現行はプレイ位置の中で種類が分かれておらず、印が一度に出て混乱する）。

### 4.3 レッテル表

- 新しい部屋を見つけたら登録だけをし、出来事（例：`rooms_added`）で特徴（H の場所の種類、名前）を Muse に渡す。Muse は手が空いたときにレッテル（何用の部屋か、雰囲気、過ごし方の参考）を書く。起動は推論待ちにしない。
- 置き場所は §1.4 のとおり（原作分はリポジトリ、Mod 分は各 PC の手元）。書き込み口は §1.4 のレッテル専用の口を使う。

## 5. 呼ぶ・連れていく

現行の「声をかける」（同じ部屋にいるユーザーの存在を知らせ、その場で外出行動を終える処理）とは別の要求として設計する。

### 5.1 呼ぶ

- ユーザーの操作は出来事として届く。アプリはその際、彼女の今の状況（トイレ・シャワー・自慰の最中、お出かけの種類など）と、いま中断できるか（例：シャワー中は不可）を添えて Muse に知らせる。彼女を勝手には動かさない。押した直後はアプリが「呼びかけを受け付けた」と示す。呼びかけが続けて来たら、まとめて1回として知らせる。
- 応じ方は Muse が決める。想定は3つ：すぐ向かう／声だけ先に返して、切り上げてから向かう（トイレ・シャワー）／続けるか切り上げるかを判断する（自慰）。別の部屋から声だけ返す台詞の形が現行にあるかは確認事項（在席と独り言の仕組みとの関係を見る）。
- 「終わってから行く」移動は、実行の前にキャラ変更・セッション終了・呼びかけの取消を確認してから動かす。Muse の返答が遅れた場合に備え、受付済みの表示と取消の手段を用意する。

### 5.2 連れていく

- Muse のブロックの場所移動に「一緒に」を足す。提案とユーザーの承諾と、移動の実行を区別する。部屋の移動は今は一瞬なので、二人で出ていく短い動きか暗転を挟む。
- 外出中・プレイ中・移動中にどう扱うか（割り込み可否）を決め、今の位置や行動が勝手に飛ばないようにする。

## 6. 口の動き

- 構造：アプリがセリフを表示する開始の合図で、その文の読みを口の部門へ渡す。表示した割合に読みの進み具合を合わせ、句読点（「、」「。」）で口を閉じて一拍置く。一押しで全文を出したときは口も止める。文字送り・早送り・中断に追従させる。
- 読みの準備は表示待ちの間に済ませ、表示開始の瞬間に重い処理を始めない。
- 読みの付け方：本文にルビ形で添える（例：`漢字《かんじ》`）。アプリは表示から読みを除き、口には読みを使う。（）の内心を除く処理と同じ所で扱う。読みが無い部分は、文字送りに合わせた開け閉めで代替する。
- **注意（対戦）**：対戦ではブリッジが（）を除いてから相手に送る。ルビも同じ所で扱わないと、相手の画面に `《》` が出る。
- **見積もり事項**：アプリ側で漢字や固有名詞の読みを作る処理は、現行には無い（現行の整形は主に（）の内心除去）。「容易」とは言い切れないので、ルビ形を本命とし、アプリ側の読み生成は任意の補助として量を見積もる。
- 口形と口の開きは表情側も操作するため、優先順位は §2 の表情整理と一緒に決める。

## 7. アイテムと酩酊

前提（2026-11-05 の決定の続き）：「飲むなら現物が要る」。効果はアプリ側の仕組みとして作り、Muse の言葉で数値を動かさない。

- 気分に「酩酊」を足す。アイテムは表（例：`items.json`）に持ち、効き方は「時間をかけて上がり、引く」形にする。酒・コーヒーは尿意、媚薬は発情、酒は酩酊を上げる。
- 口の分け方は B 案：ユーザーが勧める（出来事として知らせる）／受けるかどうかは Muse が決める／飲んだ・使ったは Muse のブロックでアプリが効かせる。
- 酩酊・発情などの身体状態は Muse に渡し、その人物がどう振る舞うかは Muse が判断する。酩酊の見せ方（頬の赤み・目の開き・まばたき・視線のゆらぎ）は原作の表情の部品で出す。
- 決めること：誰が使ったか、数量、効果量、持続時間、重ねた場合、再起動後の扱い。同じ使用指示の再送で二重に消費・加算しないこと（依頼 ID の作法にそろえる）。

## 8. 実時間連動と時計

- PC の時計から朝・昼・夕・夜を決める。段階的に足す：最初は時計の表示切替と、状態に今の時間帯を載せて Muse の挨拶・話題・行動判断に使うところまで。部屋の明かりの切替は、スタジオのマップの時間帯切替がどこまで使えるか確認してから。
- 時計を隠しても時刻連動は使える形にする。
- 決めること：日付変更・PC の時計変更・スリープ復帰の扱い。既存の「アプリを閉じている間の気分」の規則（契約 1.18 の落ち着き）と整合させる。

## 9. 最終形（今回の対象外。備えのみ）

- 方針は決まっている：後の課題とし、取りかかると判断した時点で、Alpha をレガシーとして残し、Alpha2 のリポジトリを立てて始める。
- 前提の確認（Claude・GPT）：現行プラグインは原作のコードを写しているのではなく、その場で呼んで使っている。「移植」は作り直しの量が非常に大きく、原作のコードを読んでから書き直すと派生物とみなされる恐れがある。やる場合は、動きの観察と公開の情報だけから作る形が要る。
- 今のうちの備え：(a) 原作のコードに深く頼る部分を、必要以上に増やさない。(b)「舞台が満たすべきこと」（キャラ・服・動き・部屋・表情・口）を、気づいたときに短く書き留める。(c) 今回追加する衣装・部屋・アイテムの識別方法とデータ形式は、Alpha2 でも引き継げるよう整理しておく（§1.3 の ID の決め方はその一部）。

## 11. レビューで決めてほしい点

- **D1 表情の保持の単位**：案A（次の指定か場面転換まで＋短秒ラベルだけ時間戻し＋安全時間）か、案B（表示中かつ表情秒数まで）か。

- **D3 部屋の ID の作り方**：Mod の部屋の安定した識別子を何から作るか。
- **D4 レッテルの書き込み口の形**：ブリッジの API とするか、別の経路にするか。対象は部屋と衣装の両方。
- **D5 衣装レッテルの鍵**：コーデカードの改名・差し替えでレッテルをどうするか（ファイル名鍵か、内容の要約値か）。
