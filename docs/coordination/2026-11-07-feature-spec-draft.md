**状態：仕様案（第3版。採用範囲と残りの決定を反映）**。2026-11-07 の相談をまとめた第1版に、GPT と Claude のレビュー、ユーザーの決定、そして採用範囲の決定（§0）を反映した。実装引き継ぎは、この版の後で、アプリとブリッジの範囲（Claude へ）と Muse 側の範囲（スキルの反映）に分けて別途行う。

## 0. 採用範囲（ユーザー決定、2026-11-07）

- **採用**：§1（表の型）、§2（表情）、§3（衣装）、§4（部屋）、§6（口）、§7（アイテム）、§8（時刻。ただし時計表示のみの縮小形）。
- **棚上げ**：§5（呼ぶ・連れていく）。理由：アプリ上でユーザーと Muse の双方に既に移動能力があるので、Muse の推論任せでも成り立つ可能性がある。§9（最終形）は引き続き棚上げ。
- §1 は、既存の引当表とレッテル表の実装（プレイのカタログと要約表の組）と考え方を合わせる。
- 本書で「決定」と明記したものが仕様であり、それ以外の書き方は実装方式の提案として、実装時に調整できる。Muse が守る手続き（ルビを書く、レッテルを API で書く、表情の指定中と表示中を状態で読む）は、スキル側の反映として別の PR で扱う。

この案で扱う項目：1 表情の優先順位、2 衣装（コーデカード）、3 部屋の自動登録と位置編集、4 呼ぶ・連れていく、5 口の動き、6 アイテムと酩酊、7 実時間連動と時計。最終形（原作部分の移植とインストーラー）は §9 に備えだけを書き、今回の実装対象にはしない。

全体を通る既存の原則は変えない：アプリは知らせ、行動は Muse が決める（B案）。体の数値はアプリの仕組みだけが動かす（数値従属）。操作は「画面で確定する即時操作」と「チャットで依頼する操作」の二分法に従う。

## 1. 表の整理（引当表とレッテル表）

今回の項目のうち衣装・部屋は「一覧から選ぶ」機能で、プレイには既にある二表の分離（カタログ＝引当、要約表＝レッテル）を、衣装と部屋にもそろえる。混ざると壊れるので、先に型を決める。

### 1.1 二つの表の役目

| | 引当表 | レッテル表 |
|---|---|---|
| 答えること | 何があり、今できるか（存在・可否・位置・機能） | それがどんなものか（用途・雰囲気・過ごし方の参考） |
| 作り手 | アプリ／ブリッジが生成する（原作・Mod・カード資産から導出） | 人と Muse が書く（説明文） |
| 正しさの基準 | 実装と一致すること。可否の判断はこちらが正 | 判断材料。誤っていても可否は壊れない |
| 結ぶ鍵 | 対象の安定した ID（下記 1.3） | 同じ ID で引当を指す |
| 置き場所 | アプリ内のデータと API（`GET /api/catalog` 等） | ファイル（リポジトリ、または各 PC の手元。下記 1.4） |

### 1.2 対象ごとの現状と、この案での形

- **プレイ**：引当＝カタログ（`catalog.plays`／`catalog.available`）、レッテル＝ `MUSE_GUIDE_plays.md`（既存、215件）。変更なし。スキル側の使い分けは PR #38 で追記済み。
- **部屋**：引当＝新設する部屋の登録情報（ID・名前・取得できた対応位置とその種類・実行できる機能）。レッテル＝新設（§4.3）。今は固定5部屋の一覧が引当を兼ねているので、登録が自動化されるのに合わせて分ける。
- **衣装**：引当＝コーデカードの一覧（ID・名前・サムネイル）。レッテル＝新設（§3.3）。カード内の衣装7組は使わない（ユーザー所見：階層が深く管理が面倒）。

### 1.3 鍵（ID）の決め方

- 引当とレッテルを結ぶ ID は、**一覧の並び番号に依存しない**こと。Mod の追加・削除で番号がずれると、レッテルが別物を指す。
- 部屋：原作の部屋は原作由来の安定した識別子を使う。Mod の部屋は、導出時に決まる安定した識別子（マップの識別情報から作る等。作り方は Claude の確認事項）。
- 衣装：コーデカードのファイル自体を鍵にする（ファイル名または内容の要約値）。カードの差し替え・改名でレッテルがどうなるかは §3 の決定点。

### 1.4 レッテル表の置き場所と書き方

- **事前に用意するレッテル**：既知の部屋（原作の部屋と、その環境で既に知れている Mod の部屋）は、Claude が事前に推論して用意する。用意する範囲と、配布物に含めるかどうかは別の話として分けて書く：原作の部屋のレッテルは誰の環境にもあるのでリポジトリに置ける（プレイ要約表と同じ）。特定の環境の Mod の部屋のレッテルは、その PC の手元のファイルに置く。
- **その PC のコーデのレッテル**：環境ごとに違うので、各 PC の手元のファイルに置く。配布物には含めない（ユーザーのカード資産と、その環境の記録のため）。
- レッテルに書くのは、公開できる ID と説明だけにする（PC の絶対パスやカード本体は含めない）。対象が無くなったレッテルは消さずに保管して適用を止め、再登録されたら戻せるようにする。共有の説明とユーザーの直しが競合したら、ユーザーの直しを優先する。
- **新規分の書き方**：登録だけ先に済ませ、特徴が出来事で Muse に届いてから、Muse が手の空いたときに書く（§4.3）。レッテルが無い（未整理）対象も、引当の範囲ではそのまま選べる。書いたレッテルはユーザーが直せる。
- **Muse の書き込み口**：レッテルを書き込むための口が要る。形はブリッジのレッテル専用 API（例：`GET`・`POST /api/labels/rooms`、`…/coordinates`。Muse の鍵だけ。書いたものは PC の手元のファイルに保存）。引当に登録されていない ID への書き込みは断る（ブリッジはアプリの一覧を持っている）。作者が使う Muse 専用の受け口でも通るよう、経路と権限をそろえる。同時編集の競合の検出も設ける。
- **ずれの検査**：存在しない ID を指すレッテルは落とす（または未整理として報告する）。レッテルが無い引当は正常（未整理）として扱い、検査では落とさない。

### 1.5 使い方の原則

- 選ぶときの可否は引当だけで決める。レッテルは「どれが相応しいか」の判断材料にだけ使う。
- レッテルに書かれた推論（例：「プールらしい部屋」）と、引当の事実（プール用の位置が取得できているか）は混同しない。機能が要る場面では引当を見る。

## 2. 表情

### 2.1 現状（確認済みの事実）

Muse の表情はブロックの `emotion.label` で届き、原作の表情へ変換される。その上でアプリが機械的に変える場面がある：ラベルごとの秒数で場面の既定へ戻る／プレイ中の既定は快感度ゲージで決まる（0.5 未満 `flushed`、以上 `aroused`）ため長いプレイでは Muse の表情はすぐ消える／場面転換で既定へ戻る／接触反応・絶頂・余韻はアプリ優先。プレイ中の視線と首は原作の制御、頬の赤みは表情指定と身体状態の双方から決まる。時間戻しの仕組みは、試運転5・7の所見（絶頂の閉じた目が次のパッケージまで残った）への対応として入った。

### 2.2 形（決定済み：ユーザー、2026-11-07）

層は2つにする。アプリの自動表情は今まで通り動き続け、その上に Muse の指定を重ねる。指定がある間は指定が勝ち、無い間は今まで通りがフォールバックとして働く。優先順位と保持期間を分けて書く。

- **優先順位**：Muse の表情が保持されている間、ゲージで決まる既定の表情は上書きしない。接触反応・絶頂などの一瞬の表情だけが一時的に割り込み、終わったら Muse の表情へ戻る（戻す顔を1つ覚えておく。触れたときの戻し先を覚える既存の仕組みと同じ所に置ける）。
- **保持期間**：Muse の表情は、次の Muse の表情か場面の切り替えまで保つ。一瞬の表情に使う短い秒数のラベル（`ecstasy` など）だけは時間で戻り、戻り先はゲージの既定ではなく直前の Muse の表情。保険として長い安全時間（数分）で既定に戻す（Muse が何も送らなくなったときの固着防止）。安全時間は受付の時刻からではなく、その Muse 表情の保持が始まった時刻（表示の開始）から数える。一瞬の表情が出ている間も、起点は保持中の Muse 表情の始まりのままとする。
- **場面の切り替えのとき**：保持中の表情、戻し先の記憶、安全時間の数えを、まとめて消す。
- **決めた理由（ユーザー）**：Muse の指定表情とアプリの自動表情は、人間の目にはニュアンスの違いが違和感になるほど大きい。保持が長い方が、その差が見えてしまう機会が減る。また、指定の表情が出ている間に次の表情を待てるので、表情の移り変わりの隙間にフォールバックが割り込んで変に見える懸念も、こちらの方が小さい（無くなるわけではない）。

対案だった案B（効くのは表示中かつ表情秒数まで）は採らない。プレイではパッケージの合間にゲージの既定へ戻り、今回の違和感（長いプレイで Muse の表情がすぐ消える）が残るため。

### 2.3 追えること（点検可能性）

状態で「Muse が指定した表情」「現在表示している表情」「一時変更の理由と終了条件」を確認できるようにする。既存の `emotion`（アプリが適用したラベル）の意味は変えず、指定側を別に持つ形が候補。

## 3. 衣装（コーデカード）

### 3.1 形

- コーデカードを読む。対象はコーデカードのみに絞る（カード内の衣装7組は使わない）。
- **事実：コーデカード（`ChaFileCoordinate`）に入るのは、服・アクセサリー・化粧（有効なとき）だけ**で、髪は入っていない（髪は体の側 `ChaFileCustom`）。したがって適用範囲に髪の話は無い。髪のアクセサリーはアクセサリーとして入る。
- **カードの置き場所（決定済み：ユーザー、2026-11-07）**：対象はアプリ側の `game/UserData/coordinate` に置かれたカードのみ。原作の側のフォルダは読みに行かない。理由：後の独立化を考えると、原作の置き場所への依存を新しく作らない方がよい。
- 着替えの口は2つ：ユーザーの画面操作と、Muse のブロック。どちらも同じ適用処理を使う（原作のスタジオの衣装読み込みの処理を使えば、Mod の拡張データも KKAPI の仕組みでそのまま当たる見込み）。
- 着替えたら、既存の出来事 `outfit_changed` で知らせる。
- 互換：契約に今ある「カード内の番号を指定する着替え」（`{kind: "change", outfit: n}`）は急に消さず、`coordinate`（カードの指定）を足して `outfit` は当面そのままにする（契約は小数の版で足せる）。
- プレイ中・対戦中の着替えは、操作として出さない扱いにする（ブリッジ側の拒否としては書かない。アプリ側で確定させる必要がある場合は、既存か追加の拒否の語彙へ振り分ける）。
- カードの読み込み自体が失敗した場合は、着替えずに、理由を出来事などで返す（次の §3.2 の「置き換わり」とは分けて扱う）。

### 3.2 「欠け」の扱い（決定済み：ユーザー、2026-11-07）

「欠け」を欠陥として扱う案（欠けたら着替え前の姿を保つ／欠けた一覧を警告として出す）は、どちらも採らない。

- **スロットが空なのは、コーデの構成そのもの**である。本構想は成人向けで、下着を付けない等の構成も意図して作られたコーデでありうる。指定が無いものを「かけた」とみなして扱いを変えない。カードのとおりに着せる。
- 部品が参照する Mod 等が環境に無い場合は、環境側の事実として、キャラカードで既に行われている扱い（原作の品への置き換わり）に従う。これは着替えを断る理由にしない。置き換わりが起きたことは、引当側の情報として分かるようにするに留める。
- 衣装を読み込んでも人物 ID や性格は変わらないことを条件に入れる。

### 3.3 レッテル表

Muse が場面に合わせて選べるよう、各カードに名前とは別の説明・用途のタグをレッテル表（§1）に持つ。置き場所は各 PC の手元（カード資産が手元のものため）。タグはユーザーが付け、Muse が提案・追記できる形が候補。

## 4. 部屋（自動登録と位置編集）

### 4.1 自動登録（決定済み：組み合わせ案、ユーザー支持）

- 原作と Mod の部屋を、起動時に登録する。登録のしかたと保持のしかたは分ける。
  - **登録は名前だけを起動時に行う**（原作の表から速く取れる）。特徴（対応位置）は「未確認」にしておく。
  - **特徴は、その部屋を初めて読み込んだときに取って覚える**（H の場所はマップを読み込んで中を見ないと分からない。全部の部屋を先に調べると、Mod の部屋が100を超える環境では合わせて数分かかる。全部を先に調べたいときだけ、別の調べの命令を用意する）。
  - **保持（実体化）は、従来の生活用の部屋は今まで通り保持し続け、追加分から遅延読込にする**。遅延の部屋は、ユーザーの訪問のときだけでなく、彼女がその部屋で行動を始めるとき（トイレ・シャワー・着替えなど）にも用意する。ユーザーと彼女が別々の部屋にいる間は、両方の部屋を維持する。
- 起動時に追加・変更を検出し、必要分だけ更新する。新しく原作側で増えた部屋も、都度生成のタイミングは起動時でよい。
- 部屋名から機能を推測しない。取得できた対応位置（H の場所の種類＝床・ベッド・椅子・浴槽・トイレなど）を登録し、取得できないものは「未確認」として扱う。原作の H の場所を持たない Mod の部屋は、その場だけで使える部屋になる。
- **登録と「利用できる」は区別する**。「利用できる」のは、その部屋の読み込みが済んだ時点からとし、読み込みが終わる前に、その部屋を使う操作（移動・外出の開始など）は受け付けない。読み込めない部屋を、使えるものとして知らせない。
- いつもの部屋以外への移動は読み込みに数秒かかる。その待ちには暗転を兼ねられる。
- Muse に見せる部屋の一覧は「いつもの部屋」と「全部」に分ける。

### 4.2 位置の編集

- 位置の層を3つに分ける：生成時の初期値／ユーザーが保存したデフォルト（「今の位置をデフォルトにする」）／現在値。「デフォルトに戻す」と「初期化（初期値へ戻す）」は別の操作にする。
- 編集済みの絞り込みを持たせる。編集済みの判定は、座標が原点かどうかだけでなく、調整を保存した記録で持つ。
- プレイ位置は種類（床・椅子・壁など）で絞り込み、選んだ種類の印だけ表示する（現行はプレイ位置の中で種類が分かれておらず、印が一度に出て混乱する）。1つの位置が複数の種類で使われる場合は、同じ位置を共有し、分類ごとに別の座標を増やさない。

### 4.3 レッテル表

- 既知の部屋（原作の部屋と、その環境で既に知れている Mod の部屋）のレッテルは、事前に推論して用意する（§1.4。ユーザーの所見に合わせた形）。ここで Claude が事前に用意できるのは、Claude が確認できる環境（作者の環境）の話である。他の環境の既知分は、その環境の Muse や Claude が、登録のあとに書く。用意する範囲と、配布するか手元に置くかは分けて扱う。
- 新しい部屋を見つけたら登録だけをし、出来事（例：`rooms_added`）で名前を Muse に渡す。特徴が取れた時点は別の出来事（例：`room_features`）で渡す。Muse は手が空いたときにレッテル（何用の部屋か、雰囲気、過ごし方の参考）を書く。起動は推論待ちにしない。
- 書き込み口は §1.4 のレッテル専用の口を使う。

## 5. 呼ぶ・連れていく（棚上げ）

**状態：棚上げ（ユーザー、2026-11-07）**。理由：アプリ上でユーザーと Muse の双方に既に移動能力があるので、専用の呼び寄せの仕組みを作らなくても、Muse の推論任せで成り立つ可能性がある。以下は検討の記録として残す（声の届く範囲の項目も、この棚上げに伴い対象外）。

現行の「声をかける」（同じ部屋にいるユーザーの存在を知らせ、その場で外出行動を終える処理）とは別の要求として設計する。

### 5.1 呼ぶ（決定済み：受付から完了までの形、GPT 案を採用）

- ユーザーの操作は出来事として届く。アプリはその際、彼女の今の状況（トイレ・シャワー・自慰の最中、お出かけの種類など）と、いま中断できるかを添えて Muse に知らせる。中断できるかは、行動の種類だけで決めず、進行の状態に合わせてアプリが返す。彼女を勝手には動かさない。
- 受付から完了までの形を決める。押した直後はアプリが「呼びかけを受け付けた」と示し（受付の表示と、移動の完了は区別する）。呼びかけには要求の識別を持たせ、まとめて知らせる範囲は同じ起動・同じキャラ・同じ呼び先のときに限る。取消した要求への遅れた回答では、彼女を動かさない。
- 応じ方は Muse が決める。結果は3つ：すぐ向かう／声だけ先に返して、切り上げてから向かう（トイレ・シャワー）／今回は応じない（自慰を続ける等も含む）。
- 「終わってから行く」移動は、実行の前に、キャラ変更・セッション終了・呼びかけの取消を確認してから動かす。その間にユーザーが別の部屋へ移っていたら、最初の部屋へ行くのか再確認するのかを決める。Muse の返答が遅れた場合に備え、受付済みの表示と取消の手段を用意する。
- **声だけ返す台詞の形**：現行では、独り言だけが「ユーザーが彼女の部屋にいるときだけ聞こえる」規則で、ふつうのセリフは彼女が別の部屋にいても同じ枠で出る。声だけの返事には新しい印が要る（例：パッケージかブロックに `away: true` を付け、名札を「（浴室から）」のように出す）。この声がどこにいても聞こえることにするかは未決定（案：家の中の声として、部屋を問わず届く）。

### 5.2 連れていく

- Muse のブロックの場所移動に「一緒に」を足す。提案とユーザーの承諾と、移動の実行を区別する。部屋の移動は今は一瞬なので、二人で出ていく短い動きか暗転を挟む。
- 外出中・プレイ中・移動中にどう扱うか（割り込み可否）を決め、今の位置や行動が勝手に飛ばないようにする。

## 6. 口の動き

- 構造：アプリがセリフを表示する開始の合図で、その文の読みを口の部門へ渡す。表示した割合に読みの進み具合を合わせ、句読点（「、」「。」）で口を閉じて一拍置く。一押しで全文を出したときは口も止める。文字送り・早送り・中断に追従させる。
- 読みの準備は表示待ちの間に済ませ、表示開始の瞬間に重い処理を始めない。
- **パースの一元化（決定済み：ユーザー、2026-11-07）**：読みと表示文の振り分けは、表示する側のパースで一元的に行う。アプリは、届いた文がどこから来たか（自分の Muse のパッケージか、対戦で相手から届いたものか、リプレイの再生か）を見ておき、Muse から届いたものは自他を問わずパース部門へ渡し、パースした後の文をセリフとして扱う。対戦やリプレイのために読みを届ける別の経路は設けない。（）の内心も、同じパースで表示と口の両方から除く。チャットへの同文提示も、同じパースを通した表示用の文を出す（読み手が目にする文を統一する）。
- **読みの付け方（推奨形）**：本文にルビ形で添える（例：`漢字《かんじ》`）。理由：読みを添える場所がそのまま文字の位置になるので口のタイミングと表示位置が合い、足す文字量が一番小さい（漢字の読みだけ）。読みを別の項目に全文分添える形は、推論の量が増え（かなで全文をもう一度書く）、表示文との対応付けも曖昧になるため採らない。ルビは任意とし、無い部分は文字送りに合わせた開け閉めで代替する。
- パースは（）の内心を除く処理と同じ所に置く。表示の秒数・文字送り・字数の目安は、ルビを除いた表示の文字で数える。
- **見積もり事項**：アプリ側で漢字や固有名詞の読みを作る処理は、現行には無い（現行の整形は主に（）の内心除去）。「容易」とは言い切れないので、アプリ側の読み生成は任意の補助として量を見積もる（本命はルビ形）。
- 口の動きは、初めは開き具合だけにする（声の口の動きと同じ仕組み）。表情の口の形を変えないので §2 とぶつからない。母音ごとの口の形まで出せるかは、原作の口の型を調べてから決める。

## 7. アイテムと酩酊

前提（2026-11-05 の決定の続き）：「飲むなら現物が要る」。効果はアプリ側の仕組みとして作り、Muse の言葉で数値を動かさない。

- 気分に「酩酊」を足す。アイテムは表（例：`items.json`）に持ち、効き方は「時間をかけて上がり、引く」形にする。酒・コーヒーは尿意、媚薬は発情、酒は酩酊を上げる。
- 口の分け方は B 案：ユーザーが勧める（出来事として知らせる）／受けるかどうかは Muse が決める／飲んだ・使ったは Muse のブロックでアプリが効かせる。
- 酩酊・発情などの身体状態は Muse に渡し、その人物がどう振る舞うかは Muse が判断する。酩酊の見せ方（頬の赤み・目の開き・まばたき・視線のゆらぎ）は原作の表情の部品で出す。
- 決めること：誰が使ったか、数量、効果量、持続時間、重ねた場合、再起動後の扱い。同じ使用指示の再送で二重に消費・加算しないこと（依頼 ID の作法にそろえる）。
