# Skill と初回セットアップ手引きの調整議論（スマート化の受け皿）

> **本 PR は議論用です。** 推論スマート化の相談（PR #10）が下記のとおりまとまったことを受けて、次に、その結論を **Skill（`skills/muse_session_base`）** と **Muse 向け初回セットアップ手引き（`claude-setup/`）** へどう反映するかを議論するためのものです。修正や実装の依頼は含みません。合意が取れた調整から、スキル／手引きの修正 PR を別途起こします。

## 前提：スマート化のまとめ（PR #10 で一致した内容）

- **整理の方針**：正の所在が経路の向きを決める。体（正はアプリ）は双方向 — Muse→アプリは「依頼」（アプリが検証し、不可なら `block_refused`）、アプリ→Muse は「事実」（出来事＋状態）。心（正は Muse）は Muse→アプリの一方向で、状態の `emotion`・`relationship` は「自分が送ったものの写し」であって逆向きの経路ではない。
- **推論の減らし方**：挿入・抜去の可否、可能なフィニッシュ、速度上限、問いの頃合い（`beat.question_due`）は、既存の状態（`play`／`beat`）に計算されて載っている。まずそれを使い切るのが先で、アプリへの追加は不足が確かめられた分だけ。運用は場面別の早見表と固定の選択肢規則で回し、許可取り等の形式は固定形にする。二重処理の防止と ack はイベント ID に基づく固定手順にする。
- **`notable` の位置づけ**：出来事に目安が付く場合も、それは起床の候補を絞るためのもので、場面での意味の判断は Muse が元の出来事を参照して行う。
- **計測**：場面ごとに「イベント到着から起床」「状態・資料の読み込み」「生成から表示」を分けて測り、次に減らす処理を判断する。
- **実態の訂正（反映済み）**：`play.end: true` はアプリに実在する（契約の記述は対戦の節のみ）。変化速度の設定値は PR #11 で実装済み（画面設定・`settings_changed`・状態 `settings`）。Muse からの変更の口は PR #9 に設計案の段階。
- **棚卸し表（引当表）**：状態を読む・操作を頼む・実行結果や拒否を受け取る、の欄立てで操作ごとに引く表は、単なる表としてそのままでよい（体裁の変更は議論の対象にしない）。

## 議論 A：Skill の調整

特に、双方向と一方向を実装と整合させたい。

1. **経路の記述の整合**：スキルの各操作の記述が、実装の実態と合っているか。現時点で確認している不整合の例：
   - `play.end` がスキルに未記載（アプリには口があり、契約の記述は対戦の節のみ）。通常プレイで正式に使うには、遅れた終了指示が別のプレイを止めないよう、対象の起動・キャラ・プレイを実行時に照合する条件の合意が要る（GPT の指摘）。合意の形が決まれば、スキルには「いつ・どの条件で終わらせるか」を書く。
   - 一時停止・プレイ終了・セッション終了は、結果と見回りへの影響が異なる別操作として、スキルでも区別して書く。
   - 変化速度の設定値：状態 `settings` の読み方と、`settings_changed` が届いたときの反応（持ち主への報告の仕方）がスキルに無い。Muse からの変更の口（PR #9 の設計案）の採否が決まれば、その使い方も要る。
   - 心の一方向の明記：`emotion`・`relationship` の写しを「アプリからの入力」と読まないこと、宣言（satisfied 等）の引き金は体の事実であること、を運転の記述に正しく置く。
2. **早見表の置き場**：場面別（会話・プレイ・お出かけ・対戦）の早見表を、スキルの参照資料として持つか、契約から作られるものとしてスキルは参照だけにするか。正は契約に残す前提で、二重管理にならない形を決めたい。
3. **固定形と固定手順の同梱**：許可取り・提案の骨格、ack の固定手順、ウェイターの張り方（再開 ID の引き継ぎを含む）を、スキル側の手順としてどこまで確定させるか。
4. **線引き**：どこまでをスキルに書き、どこからを各 Muse の判断に残すか（書きすぎは別の肥大化になる）。

## 議論 B：初回セットアップ手引き（claude-setup）の調整

1. **契約の読み方**：新しく来た Muse が契約の全文（1,100 行超）を毎回読む前提から、場面別早見表を主とし、必要なときに契約の該当箇所を引く読み方へ、手引きを寄せるか。
2. **セットアップ手順への反映**：ウェイター監視（§3）の手順と、早見表の用意の仕方、スキルの導入順を、手引きの中でどうつなぐか。
3. **反映のタイミング**：play.end の正式化や設定値の口など、合意待ちの項目は、決まったものから手引きへ反映する順序。

## 進め方
